# Выполнение встроенного макроса на языке

## Question

Как выполнять написанный на языке `cond` на общем этапе раскрытия для eval, JS и Java, и какой минимальный набор возможностей языка нужен его определению?

Сопоставить переиспользование существующего evaluator с минимальным отдельным механизмом, проверив зависимости модулей и риск циклического bootstrap. Выбрать подход на основании текущего кода, а не предполагать необходимость нового интерпретатора.

Отправные точки: `frontend/desugar.ml`, `frontend/builtin_macros.ml`, `backend_eval/eval.ml`, `bin/runner.ml`. Результат должен позволить определить контракт форм в билете [«Представление входа и результата макроса»](02-forms.md).

## Research — 2026-11-08

Исследован локальный код; внешние источники не требуются. Ниже сохранены факты и первоначальная рекомендация; принятое после обсуждения решение записано в секции Resolution.

### Существующие возможности

- `bin/runner.ml:5–18`: раскрытие происходит до выбора eval/JS/Java; для этих targets достаточно одного compile-time механизма. Runner также обслуживает FEX, что следует учитывать при подключении общего раскрытия.
- `frontend/desugar.ml:3–19`: макрос уже имеет контракт `sexpr -> sexpr option`; список обработчиков можно передать через `Frontend.parse_and_desugar ~macros`. Результат раскрывается повторно, затем обрабатываются дочерние формы. Переданный список заменяет стандартный, а не дополняет его.
- `backend_eval/eval.ml:142–180,222–238`: evaluator уже поддерживает `def`, `fn*`, `if`, `quote`, вызов функций и рекурсию через глобальное имя. `create_context` позволяет завести отдельное окружение для встроенных макросов; `apply_value` принимает готовые значения без вычисления их как кода.
- `backend_eval/eval_stdlib.ml:3,94–105,169–173`: доступны `list`, `count`, `get`, `drop`; вместе с `=` их достаточно для рекурсивного построения вложенных `if` на корректном входе.
- Вариативные параметры функций не нужны: OCaml-обработчик передаёт один список невычисленных форм. Текущий evaluator требует точного совпадения числа параметров и аргументов (`eval.ml:230–242`). Это уточняет предварительное предположение о необходимости вариативных параметров в MVP.
- `throw` evaluator не поддерживает (`eval.ml:151–152`), а `assert` сообщает только `assertion failed`. Существующую ошибку `cond: expected test/result pairs` нельзя сохранить простым использованием этих средств. Минимальные кандидаты — проверка количества форм в существующей точке диспетчеризации или маленькая внутренняя native-функция ошибки; выбор относится к контракту макроса.

### Зависимости и bootstrap

Текущий граф библиотек:

```text
language_main -> frontend, backend_eval, backend_compiler
backend_eval -> frontend, re
backend_compiler -> frontend
frontend -> angstrom
```

Источники: `bin/dune`, `backend_eval/dune`, `backend_compiler/dune`, `frontend/dune`.

Прямая зависимость `frontend -> backend_eval` создаёт цикл. Причём evaluator использует не только AST: `backend_eval/eval.ml:192–199` вызывает `Frontend.parse_and_desugar` при загрузке зависимостей через `deps`.

Минимальный кандидат на bootstrap без циклического раскрытия:

1. Разобрать встроенное определение обычным parser и раскрыть оставшимися OCaml-макросами, без `cond` и без самого нового обработчика.
2. Вычислить определение в отдельном evaluator context.
3. Подключить closure через уже существующий контракт OCaml-обработчика и `~macros`.
4. Для программы использовать этот обработчик вместе с оставшимися встроенными макросами.

Тело определения может использовать `def` и `fn` и не должно зависеть от `cond`. Имя runtime-функции раскрытия следует отличать от имени распознаваемой формы, чтобы повторное раскрытие не принимало рекурсивный вызов функции за вызов макроса.

### Существенная граница: значения evaluator не равны исходным формам

`Frontend.sexpr` хранит вид скобок, исходное написание атома и `meta` (`frontend/ast.ml:1–4`). `Eval.quote` превращает все виды скобок в `List` и удаляет метаданные (`backend_eval/eval.ml:177–180`). Поэтому схема «quote всего входа → функция → обратное преобразование» не сохраняет произвольные условия и результаты `cond`.

Это важно уже в MVP: ветки могут содержать векторы, maps, type annotations и другие макросы. `test/frontend_desugar_test.ml:148–159` отдельно проверяет метаданные `cond`. Обычная печать/повторный parse также не сохраняет метаданные.

Для `cond` не требуется разбирать внутренности условий и результатов: достаточно переносить исходные узлы без потерь и строить новые узлы `if`. Конкретное представление таких переносимых форм остаётся вопросом билета [«Представление входа и результата макроса»](02-forms.md); новый runtime-тип пока не выбран.

### Сравнение вариантов

| Вариант | Польза | Цена и ограничения |
| --- | --- | --- |
| Существующий evaluator и подключение обработчика над frontend | Переиспользует все нужные вычисления и существующий `~macros`; не вводит новый интерпретатор | Нужна единая точка композиции, которая зависит от обеих библиотек, и проведение её во все пути полного раскрытия |
| Разделить нижний frontend/AST и верхний frontend с evaluator | Позволяет сохранить удобный публичный API полного раскрытия с автоматическим `cond` | Перестройка библиотек, включая зависимость evaluator от разбора пакетов; для одного `cond` больше изменений |
| Отдельный маленький interpreter внутри frontend | Не требует зависимости от backend_eval | Дублирует `if`, функции, окружение, рекурсию и операции со списками; появляется второе подмножество языка для сопровождения |

Рекомендация: переиспользовать evaluator и сначала рассматривать подключение через существующий `~macros` на уровне над frontend. Отдельный interpreter не оправдан имеющимися потребностями `cond`.

Ограничение этой рекомендации: добавить обработчик только в runner недостаточно. Полное раскрытие вызывается также из загрузчика eval-пакетов и напрямую из тестов и публичного `Frontend.parse_and_desugar`. После удаления OCaml-версии эти пути потеряют `cond`, если не провести композицию последовательно. В решении нужно явно выбрать: отдельный верхний API полного раскрытия с переводом вызовов на него либо разделение библиотек ради сохранения нынешнего frontend API. Глобальную mutable-регистрацию через порядок инициализации не предлагаю.

### Проверка существующим CLI

Команда `dune exec language -- --target eval` успешно выполнила следующий вход (без изменений реализации):

```clojure
(def expand-cond
  (fn [clauses]
    (if (= (count clauses) 0)
      nil
      (list 'if (get clauses 0) (get clauses 1)
        (expand-cond (drop 2 clauses))))))
(str (= (expand-cond (list)) nil) " "
     (= (expand-cond '(a x b y)) '(if a x (if b y nil))) " "
     (expand-cond '(a x b y)))
```

Вывод: `true true (if a x (if b y nil))`.

Проверка доказывает наличие нужных вычислительных возможностей и рекурсии. Это не готовый макрос: здесь нет моста исходных форм, сохранения метаданных и обработки нечётного количества форм. Интеграция compile-time evaluator с JS/Java этой командой не проверялась.

### Вопрос для принятия решения

Согласовать переиспользование evaluator и выбор границы API: допускается ли отдельный верхний API полного раскрытия с обновлением его вызывающих мест, или требуется сохранить поведение публичного `Frontend.parse_and_desugar` без изменения API? В первом случае рекомендуемый путь минимальнее; во втором нужно оценить разделение библиотек до закрытия билета.

## Resolution

Пользователь подтвердил рекомендуемый подход 2026-11-08:

- Для выполнения встроенного `cond` переиспользовать существующий evaluator; отдельный интерпретатор не создавать.
- Ввести отдельный верхний API полного раскрытия, который соединяет frontend и evaluator через существующий механизм `~macros`. Перевести на него существующие места, которым требуется полное раскрытие, включая runner и загрузку eval-пакетов; соответствующие тесты обновить вместе с ними.
- Допускается изменение границы API: прежний низкоуровневый `Frontend.parse_and_desugar` не обязан самостоятельно подключать перенесённый `cond`. Прямую циклическую зависимость frontend от backend_eval не вводить.
- Функция раскрытия получает один список невычисленных форм. Для алгоритма достаточно существующих рекурсии, `if`, `list`, `count`, `get`, `drop` и `=`; вариативные параметры не нужны.
- Определение загружать в отдельное окружение evaluator с помощью оставшихся OCaml-макросов, без зависимости от `cond` при bootstrap.

Контракт сохранения исходных форм и ошибки нечётного количества аргументов уточняется в билете [«Представление входа и результата макроса»](02-forms.md). Конкретное размещение верхнего API и загрузка определения — в билете [«Загрузка cond и граница атомарного переноса»](03-bootstrap.md).
