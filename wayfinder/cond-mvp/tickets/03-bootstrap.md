# Загрузка cond и граница атомарного переноса

## Question

Где хранить определение `cond`, как автоматически загружать и регистрировать его до обработки программы и какие проверки позволят удалить OCaml-реализацию одним полезным атомарным изменением?

Учитывать выбранные [способ выполнения](01-execution.md) и [представление форм](02-forms.md), существующий prelude и общий frontend. Установить минимальный порядок bootstrap без пользовательского `defmacro` и дополнительных импортов.

Определить критерии приёмки для OpenSpec change: прежнее поведение `cond`, автоматическая доступность, работа на всех трёх targets и отсутствие прежнего OCaml-раскрытия. Использовать существующие тесты и общие `test/samples/`; при реализации после изменений тестов обязателен `make test`.

## Уточнение объёма — 2026-11-10

Пользователь добавил предварительный атомарный рефакторинг и разрешил исследовательский spike в отдельном worktree. Вместо одного change планируются два: точки расширения с сохранением OCaml `cond`, затем подключение языкового `cond` как расширения.

## Результаты прототипа

[Результаты spike: cond как расширение](../assets/spike-results.md) содержат проверенную схему pipeline, состав двух заходов, обнаруженные ограничения и итоги `make test` (568 проверок).

Практически подтверждены существующий контракт `~macros`, callback полного раскрытия в eval-контексте для вложенных `deps`, изолированный bootstrap и встраивание `.clj` в executable через Dune. Отключение регистрации расширения проверено; полное исключение из линковки не реализовано.

## Оставшиеся решения

- Зафиксировать границу отключения: достаточно ли композиционного исключения фабрики при сохранении `Syntax` в evaluator и кода расширения в сборке?
- Подтвердить достаточность нового compile-time окружения на каждый исходный файл, как в spike, без состояния между файлами.
- Определить передачу compile-time `Eval_error` через общий API/runner для всех targets, сохранив существующую диагностику `cond`.

Перечисленные вопросы разрешены в секции Resolution ниже.

## Resolution — 2026-11-10

Пользователь подтвердил границы отключения и жизненный цикл окружения. Для ошибок поручил выбрать максимально простой вариант с приоритетом корректных программ.

- Расширение отключается исключением его фабрики из списка обработчиков. `Syntax` и код расширения могут оставаться в сборке; после переноса отключённый обработчик означает отсутствие встроенного `cond`. Полное исключение из линковки и CLI-переключатель не нужны.
- Отдельное compile-time окружение создаётся на каждый исходный файл, включая файлы пакетов. Состояние между файлами и глобальный cache не требуются.
- Определение `cond` поставляется вместе с executable: исходник `.clj` встраивается через сборку, без поиска относительно cwd и без зависимости от каталога пакетов.
- Bootstrap выполняется оставшимися OCaml-макросами и существующим evaluator, в отдельном от пользовательского runtime окружении.
- Настроенный pipeline передаётся в загрузчик пакетов через callback eval-контекста; вложенные `deps` используют ту же конфигурацию расширений.
- Для ошибок не вводятся отдельный протокол расширений, новые типы ошибок, обогащение контекстом или обязательный префикс имени макроса. Сохраняются существующие проверки и сообщение о неполных парах `cond`. Достаточно распространения существующих исключений; если для обработки `Eval_error` runner потребуется общий перехват, используется существующее преобразование в `Error message`, без дополнительных обёрток. Отдельная диагностика не является задачей MVP.

### Два атомарных захода

1. **Подготовительный рефакторинг:** верхний API полного раскрытия, композиция обработчиков, callback для пакетов, перевод вызывающих мест и тесты подключения/отключения на простом OCaml-обработчике. Нынешний OCaml `cond` и поведение языка сохраняются. `Syntax` и языковые макросы сюда не входят.
2. **Расширение с cond на языке:** внутренний `Syntax`, обратный мост, bootstrap и поставка `.clj`, подключение в стандартной конфигурации, удаление прежнего OCaml-алгоритма `cond`.

Каждый заход оформляется отдельным OpenSpec change. Критерии приёмки: существующие suites проходят; расширения доступны во вложенных пакетах; перенос `cond` сохраняет результаты, порядок вычислений, метаданные, Java-аннотации и JS source maps. Основные новые fixtures проверяют корректные программы. После изменений тестов — `make test`.

Основание: [проверенный spike и его ограничения](../assets/spike-results.md). Прототип остаётся исследовательским материалом, не переносится целиком как готовый рефакторинг.
