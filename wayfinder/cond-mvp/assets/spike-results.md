# Результаты spike: cond как расширение

Зафиксировано 2026-11-10 по результатам прототипа от 2026-11-09.

Прототип: `/Users/igor/.local/share/opencode/worktree/35bff5/spike-cond-extension`.
Подробный журнал: `spike/cond-extension.md` в этом worktree. Код экспериментальный, не готовый change для merge.

## Подтверждено

- Алгоритм `cond` выполняется существующим evaluator из определения `backend_eval/macros/cond.clj`; прежнего OCaml-алгоритма и fallback в прототипе нет.
- Расширение подключается через существующий список обработчиков `sexpr -> sexpr option`, без изменения обхода `Desugar` и backends.
- Аргументы передаются одним списком непрозрачных `Syntax of sexpr`; создаваемые `List`, символы и литералы преобразуются обратно в AST. Исходные узлы сохраняют метаданные, новые получают метаданные вызова.
- Достаточно одного существующего прохода раскрытия: передача сырых форм в `Syntax` не требует предварительной нормализации скобок.
- Callback `parse_source` в eval-контексте проводит настроенный pipeline через вложенные `deps`, не создавая зависимости evaluator от модуля расширения.
- `~extensions:[]` отключает регистрацию и выполнение расширения. Остальные обработчики продолжают работать; состояние регистрации не протекает между вызовами.
- Отдельное окружение макросов изолировано от пользовательских определений.
- Исходник `.clj` встроен через Dune в executable; запуск из другого каталога без `LY2K_PACKAGES_DIR` вернул `42` для `(cond false 0 true 42)`.

## Проверки

Исходный и итоговый `make test` прошли. Итог: **568 проверок в 18 suites**, включая 317 sample/сопутствующих проверок, 54 проверки JS source maps и 5 проверок расширения. Проверены eval, JS, Java, исходные metadata/диагностика `cond`, Java-аннотация lambda, вложенные пакеты и построение новых форм. `git diff --check` прошёл.

Нагрузочная проба с 100, 1000 и 5000 ложными парами перед `true 42` успешно вернула `42`. Один запуск на размер; это не статистический benchmark и не определение предельной глубины.

## Обнаруженные проблемы и ограничения

1. **Форматтер не является сериализатором кода.** `float_text` превращает `1.0` в `1`; обратному мосту нужно сохранять числовую категорию. В spike это поймано тестом и исправлено добавлением `.0` при необходимости. Исходные узлы внутри `Syntax` не форматируются.
2. **Загрузка пакетов — отдельный вход в компилятор.** Замены вызова в runner недостаточно; нужно обновить `Eval.load_package_file` и прямые тестовые вызовы frontend.
3. **Граница ошибок.** Сейчас runner перехватывает `Eval_error` только на стадии исполнения eval. Compile-time ошибки могут возникнуть раньше и для JS/Java; общую границу обработки нужно уточнить при проектировании интеграции. Существующая ошибка нечётных аргументов `cond` сохранена.
4. **Жизненный цикл.** В spike фабрика инициализируется на каждый исходный файл. Для чистого `cond` этого достаточно; состояние макросов между файлами не обещается.
5. **Стоимость алгоритма.** Повторный `count` остатка списка создаёт квадратичную составляющую. Для чистового определения можно проверить пустоту сравнением с пустым списком, без нового builtin.
6. **Отключение не равно исключению из сборки.** `Syntax` остаётся в типе evaluator, модуль расширения — в библиотеке. Полностью независимый binary plugin не реализован.
7. **Два ограничения существующих targets.** JS сравнивает списки по ссылке; Java после `if`/`cond` может требовать явного cast результата к `Runnable`. Первые варианты новых fixtures нарушали эти ограничения. Сравнение с исходным компилятором дало идентичный генерируемый код после нормализации gensym; исправлены fixtures, не backends.

Docker image не собирался. Пользовательские макросы, операции разбора содержимого `Syntax`, гигиена и исключение расширения из линковки не исследовались.

## Рекомендуемая последовательность изменений

### Заход 1 — точки расширения без изменения поведения языка

- Ввести верхний API полного раскрытия с композиционно задаваемыми фабриками обработчиков.
- Провести callback полного раскрытия через eval-контекст и загрузчик пакетов.
- Перевести runner и соответствующие тестовые точки входа на этот API.
- Проверить подключение/отключение тестового OCaml-обработчика и его работу через вложенные `deps`.
- Сохранить все нынешние OCaml-макросы, включая `cond`; по умолчанию дополнительных расширений нет.

Самостоятельная ценность — единый pipeline и проверенная точка подключения. Здесь не нужны `Syntax`, `.clj`-макросы и мост runtime-значений.

### Заход 2 — внутренние макросы на языке

- Добавить `Syntax`, обратный мост и изолированное compile-time окружение.
- Встроить исходник `cond.clj` в сборку и подключить фабрику расширения в стандартной конфигурации.
- Удалить прежний OCaml-алгоритм `cond`, сохранив его поведение и автоматическую доступность.

Каждый заход оформляется отдельным OpenSpec change. Имена и размещение модулей spike не фиксируют окончательный публичный API.
