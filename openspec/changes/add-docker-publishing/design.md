# Design

## Context

Мотивация описана в `proposal.md`, контракт поставки — в `specs/container-distribution/spec.md`.

- `bin/main.ml` читает stdin, по умолчанию выбирает `eval`, принимает `--target` и возвращает ошибки через stderr и код 1. Обёртка для контейнера не требуется.
- `dune-project` требует Dune 3.23 и объявляет зависимости Angstrom, Re 1.13.2 и Alcotest для тестов. Executable описан в `bin/dune`, результат сборки — `_build/default/bin/main.exe`.
- `make test` вызывает `make build`, который требует `LY2K_PACKAGES_DIR` и копирует туда prelude. Этот существующий механизм используется только внутри builder.
- Согласованы Debian 12, обычная нативная сборка, первоначальная платформа `linux/amd64` и поставка только бинарника.

## Goals / Non-Goals

**Goals:**
- Изолировать сборочный и тестовый toolchain в отдельном этапе Dockerfile; в финальный этап копировать только `bin/main.exe`.
- Выполнять тесты при Docker-сборке одинаково локально и на CI.
- Предоставить стабильный путь бинарника и запускать полный suite перед публикацией.

**Non-Goals:**
- Полная статическая линковка, musl и запуск в `scratch`: отдельная будущая задача из proposal.
- Multi-platform публикация, релизные теги, установка Node.js/JDK в финальный образ.
- Встраивание пользовательских пакетов `(deps ...)` в бинарник или изменение CLI.

## Decisions

### 1. Два этапа на Debian 12

`builder` использует `ocaml/opam:debian-12-ocaml-5.3`. Наличие тега и Linux/amd64 manifest проверено через Docker Hub API при подготовке дизайна. `runtime` использует `debian:bookworm-slim`.

Общая версия Debian обеспечивает совместимую glibc для обычного нативного бинарника. Одноэтапный образ оставил бы большой toolchain в поставке; Alpine потребовал бы другой libc, а `scratch` — отложенную статическую сборку.

В `builder` работать в окружении opam и копировать исходники с владельцем, имеющим право записи в рабочий каталог. Установить Dune версии не ниже 3.23, Angstrom, Re 1.13.2 и Alcotest. Node.js 24 копировать из `node:24-bookworm-slim`, JDK 25 — из `eclipse-temurin:25-jdk-jammy`. Jammy использует glibc не новее Debian 12, что позволяет запускать этот JDK в builder. Задать `JAVA_HOME` и добавить JDK в `PATH` только в builder; JDK 25 требуется тесту instance main.

Перед запуском тестов задать `LANG=C.UTF-8` в builder: без локали базовый OCaml-образ использует POSIX, и Java stdout кодируется в ASCII. Проверка Unicode выявила эту зависимость; UTF-8 locale сохраняет корректный вывод строк.

Выполнить `RUN LY2K_PACKAGES_DIR=/tmp/language-packages opam exec -- make test`. Это собирает проект и запускает все targets; ненулевой код прекращает Docker-сборку. Используется существующий Makefile без новой логики работы с пакетами. Финальный этап зависит от builder через `COPY --from`, поэтому BuildKit не может пропустить тестовый этап. Обычное переиспользование Docker-кеша для неизменившихся исходников и тестов допустимо.

`.dockerignore` исключает `_build`, `.git`, локальное opam-окружение и настройки редактора/агента. В builder копировать Dune-файлы, исходники, Makefile, `prelude/` и `test/`, чтобы изменение любого из них инвалидировало слой запуска тестов.

### 2. Явная структура финального образа

Из `builder` копировать только `_build/default/bin/main.exe` в `/usr/local/bin/language`. Не создавать каталог пакетов и не задавать `LY2K_PACKAGES_DIR` в образе.

Использовать exec-form `ENTRYPOINT ["/usr/local/bin/language"]`, без shell-скрипта и без `CMD`, переопределяющего стандартный target. `--target` передаётся как аргумент, stdin остаётся доступным через `docker run -i`.

Системные зависимости определить по `ldd` собранного Linux-бинарника. В Debian runtime установить только недостающие пакеты с `--no-install-recommends`, если базового образа недостаточно; очистить apt lists. Не переносить системные библиотеки вручную из builder и не предполагать, что OCaml-бинарник автоматически статический.

Пользователь может наследоваться от образа через `FROM` либо копировать бинарник через `COPY --from` в совместимое окружение, предоставляя его системные зависимости. Для исполнения сгенерированных JS/Java нужны runtime-файлы из репозитория и внешний Node.js/JDK.

### 3. Один workflow и один собранный образ

Добавить `.github/workflows/docker.yml` с trigger `push` только для `main`, runner `ubuntu-24.04` и `permissions: contents: read`.

Последовательность job:
1. Checkout commit текущего события.
2. Docker Hub login: пользователь `y2khub`, token из `secrets.DOCKERHUB_TOKEN` через стандартный Docker login action.
3. `docker build --platform linux/amd64 -t y2khub/language:latest .`, включая тесты внутри builder.
4. `docker push y2khub/language:latest`.

Для checkout и login использовать поддерживаемые официальные actions. Токен используется только шагом login и не передаётся в Dockerfile, build args или build context. Не применять `continue-on-error` к сборке и проверкам.

Обычные Docker-команды достаточны для одной платформы. Workflow не устанавливает toolchain и не содержит тестовых команд: проверка принадлежит Dockerfile. Отдельный registry cache, матрица сборок и дополнительные теги пока не нужны.

### 4. Проверки и документация

При локальной приёмке проверить финальный образ; эти команды не добавляются в workflow:
- stdin-программа `(str "Hello, " "world!")` при default target и `--target eval` возвращает `Hello, world!` и успешный код;
- `--target js` и `--target java` для небольшой корректной программы успешно генерируют ожидаемые исходники; при приёмке сравнить с CLI из того же checkout;
- `--target unknown` возвращает ненулевой код и `unknown target: unknown` в stderr;
- в финальном образе отсутствуют команды `ocaml`, `opam`, `dune`, а у `/usr/local/bin/language` нет неразрешённых динамических зависимостей.

В README добавить локальную сборку, pull/run, выбор target, платформу, ограничения переноса отдельного бинарника, полный прогон тестов внутри Dockerfile и настройку `DOCKERHUB_TOKEN` с правом записи в `y2khub/language`.

При реализации проверить успешный полный `make test` в Docker-сборке и убедиться на временном контексте с намеренно неверным ожидаемым выводом sample, что ошибка теста останавливает сборку. Тестовые инструменты не попадают в финальный образ.

## Risks / Trade-offs

- [Динамические зависимости бинарника] → проверить `ldd` и запуск именно финального образа, установить недостающие Debian-пакеты.
- [Изменяемые базовые теги и opam-репозиторий] → версии toolchain и ОС выбраны явно, Re закреплён проектом; тесты включены в сборку. Побитовая воспроизводимость не входит в текущий контракт.
- [Несколько одновременных push] → `latest` обозначает последний успешно опубликованный образ; порядок завершения workflow может отличаться от порядка commit. Строгая упорядоченность публикаций сейчас не гарантируется.
- [Недоступный registry или неверный secret] → штатная ошибка login/push делает job неуспешным; повторный запуск workflow после устранения причины.
- [Локальный ARM-хост] → использовать `--platform linux/amd64`; для запуска и проверки требуется поддержка эмуляции Docker. CI использует нативный amd64 runner.

## Migration Plan

1. Добавить Dockerfile, `.dockerignore`, workflow и README, проверить сборку и контейнер локально.
2. Подготовить репозиторий Docker Hub `y2khub/language` и GitHub Actions secret `DOCKERHUB_TOKEN`.
3. После включения workflow через push в `main` проверить успешную публикацию, затем pull и запуск опубликованного образа.
4. Для отката остановить ошибочную публикацию, вернуть конфигурацию/исходники к рабочему состоянию новым commit и повторить workflow. Данные приложения не мигрируют; сохранённый digest предыдущего образа позволяет временно запускать его напрямую.

## Open Questions

- Точный набор дополнительных Debian runtime-пакетов определяется по `ldd` при первой сборке; это не меняет выбранную архитектуру и контракт.
