# Design

## Context

Мотивация описана в `proposal.md`. Eval хранит все скалярные значения как `Symbol of string`. В `eval.ml` литералы разрешаются после bindings, `quote` рекурсивно создаёт значения из AST, а `truthy` проверяет текст символа. В `eval_stdlib.ml` отдельно реализованы `not`, `assert`, равенство и текстовое представление. `get-in` уже делегирует каждый шаг в `get`.

`bin/runner.ml` возвращает только текст финального `Symbol`. Тест `compiler_ns_returns_nil` в `test/eval_ns_test.ml` также предполагает `Symbol`, поэтому одной замены runtime-конструктора недостаточно. Design нужен из-за изменения модели данных на границе нескольких модулей и runner.

## Goals / Non-Goals

**Goals:**
- Представить отсутствие значения одним конструктором `Nil` без полезной нагрузки.
- Сохранить это значение при цитировании, передаче через коллекции, функции и atom.
- Различать `Nil` и `Symbol "nil"` во всех потребителях и сохранить прежнее текстовое отображение.

**Non-Goals:**
- Отдельные типы для boolean, чисел и строк; предикат `nil?` и новые функции stdlib.
- Изменение AST, общего macro expansion и runtime JS/Java.
- Изменение приоритета bindings перед литералами, поддержки имён bindings или контракта пустых тел. В частности, `(do)` продолжает возвращать `List []`, а `Symbol "false"` остаётся ложным.

## Decisions

### 1. Конструктор в существующем типе value

Добавить `Nil` в `backend_eval/eval_types.ml`. Обёртка `option` вокруг всех значений потребовала бы менять каждую операцию и смешала бы отсутствие результата OCaml с полноценным значением языка; отдельный конструктор расширяет существующий вариантный тип напрямую.

### 2. Конвертация на границе AST и runtime

В `find` сохранить текущий порядок поиска; на этапе литералов преобразовать текст `nil` в `Nil`. Строковый атом `"nil"` по-прежнему проходит ветку строки и становится `Symbol "nil"`.

В `quote` распознавать некавыченный атом `nil` до общего случая символа. Рекурсивный обход списков автоматически распространит правило на вложенные элементы. Для атомарных ключей ассоциативной деструктуризации использовать тот же способ конвертации, например существующую `quote`, чтобы ключи `nil` и `"nil"` совпадали с соответствующими runtime-ключами. Расширять допустимый синтаксис шаблонов не требуется.

Заменить существующие результаты `Symbol "nil"`, означающие отсутствие, в `if`, `compiler/ns`, `deps`, `get` и обоих видах деструктуризации. Пустые тела и пустые списки сохраняют текущий результат `List []`.

### 3. Потребители значения

В `truthy`, `not` и `assert` ложными остаются `Nil` и `Symbol "false"`; текст `Symbol "nil"` больше не особый. В `equal_value` добавить случай `Nil, Nil`; смешанные пары ложны. Уже существующая рекурсия сравнения коллекций сохраняется. Поиск ключей через `List.assoc_opt` различает конструкторы и не требует нового механизма равенства.

В `get` только `Nil` допускает распространение отсутствующей коллекции. `get-in` получает новое поведение через существующий вызов `get`. Операции, ожидающие `Symbol`, естественным образом отклоняют `Nil`: например, `slurp nil` больше не воспринимает его как путь с текстом `nil`, но `slurp "nil"` по-прежнему может читать такой файл. Не добавлять неявное преобразование `Nil` обратно в строку для подобных операций.

### 4. Вывод и диагностика

В `to_string` добавить `Nil -> "nil"`, сохранив рекурсивный вывод коллекций. В `value_text` добавить описание `nil`, чтобы ошибка вызова `(nil)` не называла значение символом.

В eval-ветке runner добавить только случай финального `Nil -> Ok "nil"`. Использование общего `to_string` для любого финального результата изменило бы вывод списков, map, функций и atom, поэтому оно не подходит.

### 5. Проверки и документация

В существующий `test/eval_ns_test.ml` добавить целевые проверки runtime-конструктора и наблюдаемого поведения; исправить проверку результата `compiler/ns`, не ослабляя helper `last_symbol`. Проверить `deps` с пустой map или существующим тестовым загрузчиком. Проверки runner вызывают `Language_main.Runner.run ~target:"eval"` напрямую; библиотека уже подключена в `test/dune`.

Проверить литерал и quote, источники отсутствующих значений, различие от строки в равенстве/условиях/ключах, `get-in`, вывод и прохождение через atom. Специфичные для eval изменения истинности не помещать в общие cross-backend samples. Полный `make test` проверит совместимость существующих sample-контрактов.

Обновить `skills/y2k-language/SKILL.md`: описание литералов, quote, истинности, `not` и ограничений переносимости должно явно различать eval и JS/Java. Текст `"false"` в eval остаётся ложным.

## Risks / Trade-offs

- Сохранение хотя бы одного старого источника `Symbol "nil"` создаст истинное текстовое значение вместо отсутствия → проверить все такие места и тестировать сам runtime-конструктор, а не только `(str ...)`.
- Слишком широкая замена текста `nil` повредит обычные строки → отдельные проверки литерала, строки, quote и ключей map.
- Новый вариант может оставить неполные pattern matches → сборка и полный `make test` после форматирования изменённых OCaml-файлов.
- Прежний справочник ошибочно называл строки `"nil"` и `"false"` ложными на JS/Java, хотя их runtime считает обе истинными → описать фактическую совместимость `"nil"` после изменения и сохраняющееся отличие eval для `"false"`; отдельно указать различие цитирования `nil`.
- Вывод `nil` и `"nil"` остаётся одинаковым → это согласованная совместимость текстового вывода; различие проверяется через тип, равенство и условия.

## Migration Plan

Изменение поставляется одной согласованной правкой runtime, runner, тестов и справочника. Пользовательские eval-программы, использующие `"nil"` как отсутствие значения, должны перейти на литерал `nil`. Миграция хранимых данных не требуется; откат выполняется отменой этой правки целиком.
