# Design

## Context

Мотивация — proposal.md, issue #30. Коллекционные операции уже реализуются обычными runtime-функциями: `filter`/`keep` в `backend_eval/eval_stdlib.ml` и `prelude/language_runtime.{js,java}`. JS-генератор перечисляет runtime imports в `backend_compiler/js.ml`; Java использует static wildcard import и общий `call_fn`. Общие samples исполняются на всех трёх targets.

Сейчас общего compare нет: eval-предикаты порядка принимают только Int, а eval equality уже различает Int/Float и не округляет большие целые. Это не позволяет реализовать числовую сортировку простым вызовом существующего `<`. Справочник описывает эти ограничения, поэтому sort-by получает собственное внутреннее сравнение без изменения остальных операций.

## Goals / Non-Goals

**Goals:** реализовать согласованный контракт через существующие вызовы функций и сортировки стандартных библиотек; сохранить значения элементов и эффекты keyfn.

**Non-Goals:** новый проход AST, новый runtime-тип языка, общий публичный compare, собственный алгоритм сортировки, Unicode collation, универсальный порядок всех runtime-типов. Полная совместимость с Clojure не требуется: keyfn здесь вычисляется однократно.

## Decisions

### 1. Фиксированная арность и обычный binding

API — только `(sort-by keyfn coll)`. В eval добавить Native binding рядом с map/filter; на JS экспортировать `sort_by` и добавить его в существующий import; на Java добавить двухаргументный runtime-метод. Переиспользовать apply/call_fn и существующую компиляцию named/local callbacks. Альтернатива с overload или дополнительным компаратором отвергнута пользователем.

### 2. Вычислить ключи, стабильно отсортировать, извлечь элементы

```text
items --> [(keyfn(item), item), ...] --> stable sort by key --> items
```

Первый проход идёт слева направо; callback отсутствует внутри компаратора. Использовать `List.stable_sort` в OCaml, `.sort` для нового массива пар в JS и `List.sort` для нового списка пар в Java. Внутренние пары не являются новым типом языка. Java callback с checked exception вызывается до сортировки, поэтому не нужны обёртки исключений для Comparator.

Сортировать вход напрямую нельзя: это нарушает неизменность в JS/Java. Вычислять ключ внутри компаратора нельзя: нарушаются однократность и порядок эффектов. Собственная сортировка и дополнительный индекс для стабильности не нужны. Дополнительная память O(n), сортировка O(n log n) сравнений плюс стоимость вычисления ключей.

### 3. Внутреннее сравнение чисел и строк

- JS: сравнения `<`/`>` ключей одной поддерживаемой категории с нулём для равных; не `.sort()` без компаратора и не localeCompare.
- Java: строки через `String.compareTo`; обычные языковые Integer/Double сравнивать численно, без вычитания целых и с равенством обоих знаков нуля. Для существующих языковых Integer переход в double точен; произвольные host Number-подтипы не расширяют переносимый контракт.
- Eval: Int/Int и Float/Float сравнивать нативно. Смешанное Int/Float сравнение должно сохранять порядок больших Int: использовать проверку границ int перед преобразованием float в int, сравнить целые части и при их равенстве учесть дробную часть. Опираемся на подход существующего `equal_int_float`, а не на безусловное преобразование Int в float. Небольшой внутренний helper нужен только этой операции; равенство и предикаты порядка не менять.
- Eval-строки сравниваются побайтово, JS/Java — по UTF-16. Это даёт общий регистрозависимый ASCII-порядок, но не единый Unicode-порядок. Нормализации и locale нет. Keywords уже являются строковыми runtime-значениями, отдельной категории для них не вводится.

Равенство ключей определяется компаратором, а не общим `=`, поскольку mixed equality и signed zero различаются между targets. Конечные дробные значения сравниваются без epsilon.

### 4. Границы и ошибки

Для коллекций принять существующую границу filter/keep: list/vector, на JS также плотный host-массив. Nil как коллекция, maps, sparse arrays, изменение коллекции из callback и произвольные iterable вне контракта. Элементы могут быть любыми значениями, если keyfn возвращает допустимые ключи.

Проверку аргументов встроить по существующему образцу runtime, в eval — pattern matching на callable/list и Eval_error. Недопустимые категории ключей не образуют нового общего порядка. Не добавлять отдельный предварительный валидатор, AST-проход, матрицу отрицательных тестов или обещание унифицированной диагностики вне согласованного контракта. Ошибки самой keyfn передаются существующим механизмом без перехвата и отката эффектов.

### 5. Проверки и справочник

Общие fixtures в `test/samples/` проверяют числовой и ASCII-порядок, равные ключи, пустой и одноэлементный вход, исходную коллекцию, именованные/локальные/lambda callbacks и журнал Atom во вложенном namespace. Для смешанных чисел сравнивать ID элементов результата, не mixed equality ключей. Проверки возвращают `str` с бинарными `=`/`not=` по образцу `filter_keep_effects.clj`.

Целевые проверки нужны для большого Int/Float в eval, JS identity host-объектов и распространения ошибки callback с остановкой обхода. Обновить английский `skills/y2k-language/SKILL.md`: сигнатура, границы ключей/коллекций, Unicode, стабильность, эффекты и отличие от Clojure. Итоговая проверка реализации — `make test`.

## Risks / Trade-offs

- Ошибочная ничья при округлении большого Int → отдельный eval-сценарий и точное смешанное сравнение.
- Java Double.compare различает знаки нуля → численное равенство нулей должно проверяться до такого различения.
- Скрытая мутация входа → сортировать только новую коллекцию пар; проверить порядок входа и JS identity.
- Unicode-порядок отличается → явно описать границу ASCII вместо внедрения Unicode-зависимости.
- Новая функция требует обновлённого runtime → выпускать compiler/runtime вместе.

## Migration Plan

Добавление совместимо с прежними программами. После выпуска compiler/runtime потребитель заменяет host-сортировку на `(sort-by sort-key queue)` и использует возвращённую коллекцию вместо ожидания мутации. Откат — возврат прежнего вызова у потребителя и согласованной версии compiler/runtime; миграции данных нет.
