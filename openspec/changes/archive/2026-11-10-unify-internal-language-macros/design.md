# Design

## Context

Мотивация — в `proposal.md`. `Language_macros.create` сейчас устанавливает пять native helpers, загружает объединённые исходники, отдельно находит четыре функции и содержит четыре ветки распознавания. `apply_with_gensym` используется только для `and`/`or`; `cond` проверяется через OCaml `List.length mod 2`. Все функции уже принимают один список `Syntax` и возвращают значение для общего `to_sexpr`.

`Pipeline` получает фабрику типа `unit -> macro list`, создаёт её на каждый файл и ставит дополнительные обработчики перед OCaml builtins. Исходники встроены правилом Dune. Текущий `gensym` создаёт имя только при вызове native closure; установка closure не расходует счётчик.

## Goals / Non-Goals

**Goals:** удалить знание конкретных имён из механизма загрузки и вызова, сохранив текущую модель выполнения. Корректное внутреннее определение должно работать через описание без специальной OCaml-ветки.

**Non-Goals:** публичный macro API, изменяемый registry, файловое обнаружение макросов, dependency graph определений, кэш окружений, новый evaluator, общий AST framework, новая hygiene, перенос других макросов. Не разбивать небольшой модуль на набор сервисов только ради архитектуры.

## Decisions

### Approaches

Выбран согласованный вариант: статические описания и общий адаптер. Только выделить helpers в отдельный файл недостаточно — ручное подключение каждого макроса останется. Языковой registry или пользовательский `defmacro` требуют новых правил областей видимости и bootstrap, не нужных для текущей цели.

### Описание и embedding

В генерируемом `Builtin_macro_source` вместо отдельных `cond`, `and_`, `or_`, `with_open` хранить один упорядоченный список `definitions`. Элемент — простая тройка `(имя формы, имя функции раскрытия, исходный текст)`. Для четырёх элементов отдельный тип/модуль описаний не требуется. Dune продолжает встраивать `.clj` через `%{read:...}` с явными file deps; дополнительный генератор или сканирование каталога не нужны.

Имена форм и функций связываются в одном месте — этом списке. Повторение путей в build deps является требованием сборки, не вторым runtime registry. Для нового внутреннего определения достаточно добавить исходник, build dependency и элемент списка, не редактируя загрузку или диспетчер.

### Фабрика

Выделить общий `create_from definitions ()`; стандартный `create ()` делегирует ему с `Builtin_macro_source.definitions`, сохраняя текущий тип фабрики и callers. Это внутренний OCaml entry point, также позволяющий тестировать произвольные описания; не прикладной API языка.

Каждый вызов фабрики создаёт новый `Eval` context, устанавливает существующие helpers, объединяет исходники в порядке описаний и выполняет их через прежний frontend-only bootstrap. После загрузки всех определений строится список `(имя формы, значение функции)` через `Eval.find`. Не менять порядок загрузки и не разрешать зависимости через новый механизм.

Один обработчик сопоставляет Paren-вызов с символьной головой и ищет имя в этом списке. Неизвестные формы возвращают `None`; распознанные проходят через один `apply`. Сохранить порядок списка и обычный first-match поиск. Валидацию дублей, схем описаний и отдельных ошибок bootstrap не добавлять: описания доверенные и входят в сборку, корректные наборы — согласованный сценарий.

### Контекст каждого вызова

В общий `apply` перенести установку native `gensym`, захватывающего metadata текущего вызова. Затем передать список `Syntax` аргументов в `Eval.apply_value` и результат — в прежний `to_sexpr`. Удалить `apply_with_gensym`. Все макросы получают одинаковые средства; установка helper не должна сама вызывать генерацию имени.

Мутация `gensym` остаётся локальной для compile-time context, как сейчас. Каждый распознанный вызов переустанавливает его до исполнения, поэтому после ошибки следующий вызов получает новые metadata. Контекст не используется конкурентно и макросы не запускают вложенный pipeline; стек динамического контекста и синхронизация не нужны. Раскрытие вложенных пользовательских форм по-прежнему выполняет существующий desugar.

Native Syntax helpers и `macro-error` остаются локальными в фабрике. Мост, runtime-типы и `Pipeline` не меняются. `gensym` доступен во время раскрытия, а не для исполнения на верхнем уровне bootstrap-исходника.

### Проверка cond

В `cond.clj` после пустого случая проверять одиночный остаток и вызывать `(macro-error "cond: expected test/result pairs")`; затем строить прежний `if` и рекурсивно раскрывать остальные пары. Проверка пустоты `(drop 1 clauses)` отличает одиночный остаток без повторного подсчёта длины всего хвоста. Рекурсивное построение охватывает весь хвост даже после истинного условия, не вычисляя исходные аргументы.

Удалить OCaml-проверку имени `cond`. Сохранить `Failure` с тем же сообщением через существующий `macro-error`. Проверить это определение под альтернативным именем формы: такой тест отличает языковую проверку от оставшейся специальной ветки диспетчера.

### Проверки и документация

- В `test/language_macros_test.ml` подключить компактное тестовое определение под произвольным именем: возврат исходного аргумента, доступ к Syntax helpers и `gensym`, неизвестная форма даёт `None`. Это fixture через общую фабрику, не пятый поставляемый макрос.
- Проверить две позиции вызова на одном экземпляре, metadata и свежесть имён вместе с текущими `and`/`or`/`case`; отдельный вызов без `gensym` не должен обращаться к генератору (проверка эффекта, без зависимости от суффиксов `G__N`). После намеренной ошибки тот же экземпляр должен успешно раскрыть следующий вызов с его metadata.
- Тестовое определение со счётчиком в atom: последовательные вызовы одного экземпляра видят его состояние, другой экземпляр начинает заново. Существующие pipeline/deps tests проверяют создание окружения на каждый файл и отключение расширения.
- Подключить реальный исходник `cond` из списка описаний под другим именем; проверить полные пары и ошибку одного/трёх аргументов, включая хвост после `true` и эффектную исходную форму. Существующие cond tests и общие samples остаются регрессией.
- Проверить стандартные четыре макроса, без дополнительных fixtures, через существующие suites: metadata, Java-аннотации и resource cleanup, JS source maps, изоляцию и вложенные зависимости.
- Английский прикладной справочник уже описывает неизменную семантику и внутренность helpers; менять его только если обнаружено фактическое расхождение. Краткий комментарий у общего механизма должен объяснять описание и время привязки `gensym`, не обещая публичного API.

## Risks / Trade-offs

- Новый список нарушает embedding → сборка и standalone probes для всех четырёх макросов вне checkout.
- Унификация случайно расходует `gensym` на каждом вызове → проверка отсутствия эффекта у макроса, возвращающего аргумент.
- Closure сохраняет metadata первого вызова → два разных вызова одного обработчика и вызов после ошибки.
- Перенос проверки cond пропускает нечётный хвост → проверка реального определения под альтернативным именем и существующие отрицательные tests.
- Общая фабрика превращается в framework → только список, bootstrap и один адаптер; runtime-модель остаётся прежней.

## Migration Plan

Сначала перенести проверку `cond` в язык с сохранением текущего подключения. Затем заменить embedding и фабрику описаниями, объединить путь вызова и закрепить контракт тестами. Выполнить полный `make test`, standalone probes и строгую валидацию. Синхронизация, архив и коммит завершения — по отдельному запросу. Откат — отмена унификации без изменения семантики программ.
