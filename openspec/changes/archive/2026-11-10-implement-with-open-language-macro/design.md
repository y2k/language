# Design

## Context

Мотивация — в `proposal.md`. Текущий `with_open_macro` строит вложенные `let`, `try/finally` и `.close` с cast к `java.lang.AutoCloseable`. Список bindings получает metadata исходного вектора; имя, initializer и тело переиспользуются. `Frontend.is_binding_symbol` уже доступен снаружи frontend; дополнительно проверяется отсутствие `/` в имени.

`Language_macros.create` загружает три встроенных исходника через frontend-only bootstrap. `Syntax` сейчас можно только вернуть обратно; `get`/`count` работают с runtime-коллекциями, не с `Syntax`. Java-семантика подробно покрыта `test/samples/java/with_open.clj` и `with_open_errors.clj`. Проверка раскрытия в `test/frontend_desugar_test.ml` пока зависит от OCaml-макроса.

## Goals / Non-Goals

**Goals:** перенести структурный алгоритм и выбор диагностик в язык, сохранив исходные узлы и форму раскрытия; минимально расширить только compile-time окружение.

**Non-Goals:** общий публичный Syntax API, обход AST, универсальный registry, новые runtime-конструкторы, изменение управления ресурсами, bootstrap на самом языке, перенос других макросов. Развитие архитектуры — следующий отдельный этап.

## Decisions

### Approaches

Выбран согласованный перенос `with-open` с узкими native-примитивами. Оставить разбор bindings и сборку дерева в OCaml проще, но это не проверит структурный языковой макрос. Полный набор AST reflection/construction и публичные макросы преждевременны перед отдельным архитектурным этапом. `fn` затрагивает bootstrap и нормализацию паттернов, а `->`/`->>` слабее проверяют управление выполнением.

### Минимальные внутренние операции

Предлагаемые имена — внутренние детали реализации, не новый application API. Зарегистрировать native helpers локально в `Language_macros.create`, до загрузки исходников:

- `syntax-vector?`: проверяет `Syntax (SList (_, Bracket, _))`; для других значений возвращает false.
- `syntax-children`: для исходного списка возвращает runtime `List` из `Syntax` непосредственных детей; не рекурсивно и без вычисления/копирования узлов.
- `syntax-simple-symbol?`: проверяет исходный `SAtom` через существующий `Frontend.is_binding_symbol` и отсутствие `/`; остальные значения дают false. Не дублировать классификацию literal/keyword в языке.
- `syntax-list-at`: принимает исходный узел-донор metadata и runtime-список исходных `Syntax` детей, возвращает `Syntax (SList (donor_meta, Paren, children))`. Для `with-open` дети — только исходные имя и initializer; поддержка произвольных новых деревьев здесь не нужна. Новые внешние формы по-прежнему собираются через `list` и существующий `to_sexpr`.
- `macro-error`: принимает строку и вызывает существующий `Failure` с этим сообщением, сохраняя путь диагностики прежнего OCaml-макроса. Выбор сообщения и проверка структуры остаются в языковом алгоритме.

Для операций чтения/сборки достаточно обычной проверки формы аргументов в native-функции, как у текущих stdlib helpers; отдельного валидатора не требуется. Ничего не добавлять в runtime stdlib. `Syntax` остаётся непрозрачным для обычных операций языка.

### Языковой алгоритм

`expand-with-open` получает список аргументов без имени макроса. Проверяет наличие первого аргумента и `syntax-vector?`, читает bindings через `syntax-children`. Внутренняя рекурсивная функция `expand-with-open-bindings`, определённая через `def`, получает исходный вектор, оставшиеся bindings и тело; проверяет пару и имя, создаёт список bindings через `syntax-list-at`, строит `(let (...) (try rest (finally (.close (cast java.lang.AutoCloseable name)))))`. Достаточно списка Paren: существующий `let_macro` принимает его и нормализует в `let*` с сохранением metadata.

Остаток рекурсии раскрывается на compile time, но initializers и тело остаются `Syntax`, поэтому не исполняются. При отсутствии bindings непустое тело становится `(do body...)` через `concat`/`list`, пустое — `nil`. Сообщения совпадают с прежними: `with-open: expected a binding vector` и `with-open: expected simple symbol/value pairs`.

Не добавлять `gensym`: текущему алгоритму нужны только пользовательские имена. Не менять порядок `try`: initializer каждого следующего ресурса должен оставаться внутри защиты предыдущего. Не вводить пропуск nil, suppressed exceptions или дополнительные catch.

### Подключение и bootstrap

Добавить `macros/with_open.clj` в Dune embedding и загрузку фабрики, получить `expand-with-open`, зарегистрировать через общий `apply`. Bootstrap-исходник использует оставшиеся frontend формы и существующие stdlib-функции, без вызова `with-open` и без зависимости от остальных языковых макросов. Удалить `with_open_macro` и его регистрацию. `is_binding_symbol` остаётся для других обработчиков и нового helper.

Конфигурация и новое окружение на файл сохраняются через существующий pipeline. Проверку `with_open_expansion` перенести из frontend-only suite в pipeline suite; отдельно закрепить, что frontend-only теперь не раскрывает `with-open`.

### Проверки

- Прямые тесты helpers и обработчика: дети — те же исходные узлы, чтение не исполняет initializer; аннотированное имя, initializer, формы тела и вектор имеют разные metadata. Проверить несколько вызовов одного окружения с разными позициями, без привязки к новым публичным API.
- Сравнить итоговое раскрытие двух зависимых ресурсов с явными вложенными `let/try/finally`; проверить пустые bindings/тело и обе сохранённые диагностики, включая literals, destructuring и квалифицированное имя.
- Проверить default/`extensions:[]`/default, оставшийся `case`, frontend-only отсутствие fallback; изоляцию имени `expand-with-open` и всех добавленных helpers.
- Во вложенных пакетах проверять результат полного раскрытия и отсутствие нераскрытых `with-open`; для отключённого расширения — сохранённые формы. Это проверка pipeline, а не обещание исполнения Java-ресурсов в eval.
- Переиспользовать оба существующих Java samples, покрывающих порядок, аннотации, false/nil, контексты, ошибки открытия/тела/закрытия, nil и неверный ресурс. Добавить только отсутствующую проверку явного вложенного `with-open` и композиции с `and`/`or` внутри initializer/тела; не дублировать весь набор.
- JS source-map suite остаётся регрессией общего моста; не заявлять поддержку Java cleanup на JS. Metadata нового макроса проверять непосредственно по AST и через Java-аннотации.
- Обновить английские `skills/y2k-language/SKILL.md` и `references/java.md`: языковая поставка и внутренние helpers; семантика ресурсов прежняя.
- `make test`; standalone Java compilation вне checkout без `LY2K_PACKAGES_DIR` с реальным ресурсом внутри `defn test`.

## Risks / Trade-offs

- Потеря metadata при извлечении детей → сохранять `Syntax` исходных детей, явно наследовать metadata только контейнера bindings.
- Ошибка границы `try` меняет закрытие при сбое открытия → существующий `with_open_errors.clj` и сравнение core-структуры.
- Чтение `Syntax` расширяет контракт непрозрачности → только перечисленные внутренние операции; никаких изменений обычных `get`, `count` или equality.
- Helpers становятся зачатком архитектурного API → оставить локально в фабрике, без отдельного framework и обещаний стабильности имён.
- Потеря frontend-only теста при удалении fallback → перенести его в pipeline, сохранив проверки, и добавить проверку новой границы.

## Migration Plan

Добавить helpers, языковой исходник и embedding, затем удалить OCaml fallback и перенести тест раскрытия в той же реализации. Сохранить все Java regression samples. После проверок передать change на приёмку; синхронизация, архив и коммит — по запросу завершения. Откат — отмена переноса целиком, включая helpers; параллельную OCaml-реализацию не оставлять.
