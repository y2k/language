# Design

## Context

Мотивация — `proposal.md`, раздел Why. Map в eval хранится как список пар с `equal_value` для поиска; JS создаёт объект через `Object.create(null)`, Java — `LinkedHashMap<String, Object>`. JS/Java преобразуют ключи в текст. JS импортирует функции runtime явным списком, Java использует static wildcard import. Поэтому изменение затрагивает три runtime, но не frontend или lowering.

## Goals / Non-Goals

**Goals:** использовать текущие представления и обычный вызов функций; общий переносимый контракт проверять через поля и count.

**Non-Goals:** унифицировать равенство и порядок map между targets, менять hash-map/get или вводить persistent-map структуру данных. Полный API Clojure не требуется.

## Decisions

### Небольшие runtime-функции вместо новых форм

В eval зарегистрировать два Native binding в `Eval_stdlib.env`. В JS экспортировать две функции и добавить их в import `backend_compiler/js.ml`. В Java добавить статические методы с фиксированными сигнатурами. Существующие generator paths уже компилируют обычные вызовы; отдельные AST-проверки не нужны.

### Eval обновляет через существующее равенство

Минимальный общий helper над списком пар удаляет пары с ключом, равным `equal_value`, и добавляет новую пару. Assoc вызывает helper один раз, merge сворачивает пары правой map через него. Это сохраняет неизменность исходников и не накапливает записи при повторном обновлении одного поля. Конкатенация списков отвергнута: она оставляла бы старые пары и увеличивала count. `List.remove_assoc` не подходит из-за иного host equality.

Деталь реализации по умолчанию: merge обходит правые пары слева направо. Для нестандартного eval-входа с дубликатами справа последнее в обходе значение побеждает; такой вход вне переносимого контракта и не меняет существующий first-match get исходной map. Порядок пар результата не становится новой гарантией.

### Compiled targets копируют только верхний уровень

JS использует новый объект с null prototype и стандартное копирование собственных полей; assoc записывает один ключ с существующим `valueText`, merge копирует сначала left, затем right. Null prototype сохраняет безопасную запись `__proto__`. Принимаются map языка и обычные JSON-объекты; не требуется сложная классификация всех host objects.

Java создаёт новый `LinkedHashMap`, копирует исходные поля, затем выполняет put либо putAll правой map. Ключ assoc преобразуется существующим `value_text`. Вложенные значения не копируются. Обёртки immutable collections и deep clone не нужны.

### Проверки только на границе функций

Eval проверяет арности и HashMap существующим pattern matching. JS проверяет `arguments.length` и отклоняет null, массивы и скаляры в map-позициях. Java фиксирует арность сигнатурами, проверяет `Map` для аргументов. Не добавлять variadic Java overloads ради сообщений ошибок или отдельный проход компилятора. Точный текст ошибок compiled targets не фиксируется.

## Risks / Trade-offs

- Eval merge со списком пар имеет O(n*m + m²) в худшем случае → оставить простое решение для небольших записей; менять структуру map только при измеренной потребности.
- Нестроковые ключи, дубликаты и порядок уже различаются → документировать строковые/keyword ключи без дубликатов как переносимый случай; не менять старые конструкторы.
- Nil при get не доказывает наличие поля → тестировать одновременно count и типизированное равенство, а также сохранность входов.
- Новый unconditional JS import несовместим со старым runtime → поставлять compiler и runtime согласованно.

## Migration Plan

Добавить runtime-функции и JS imports, выполнить `make test`, обновить английский справочник с фиксированными арностями и примерами. Замена issue #34: `(assoc (merge item result) :selection_reason (:reason item))`. Данные миграции не требуют. Для отката вернуть предыдущую согласованную пару compiler/runtime и host-вызовы в потребителях, уже использующих новые функции.
