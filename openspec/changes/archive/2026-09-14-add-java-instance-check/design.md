## Context

Мотивация описана в `proposal.md`. Сейчас `java.ml` генерирует `cast` непосредственно, а `compile_ns` выводит Java imports без собственного разрешения классов. `bin/runner.ml` возвращает Java source, не запускает `javac`. Общий lowering обходит все элементы обычной формы и оставляет вызовы в discard-позиции самостоятельными statements. JavaScript и eval пока воспринимают `instance?` как обычный вызов.

Design необходим из-за взаимодействия Java-генератора с общим lowering и диагностикой двух других targets. Существующие требования `compiler-targets` не определяют `instance?`; изменение добавляет требования, сохраняя контракт `cast`.

## Goals / Non-Goals

**Goals:**
- Использовать семантику Java `instanceof` для динамически типизированных значений языка.
- Сохранить исходный операнд типа и корректность Java во всех требуемых позициях выражения.
- Проверять поведение имеющейся инфраструктурой Alcotest и JDK.

**Non-Goals:**
- Собственный classpath-resolver, reflection, runtime helper или эмуляция Java-типов на eval/JS.
- Динамические Class-операнды, специальный синтаксис массивов, generics и автоматическое сужение типа после проверки. Для последующего Java interop остаётся `cast` или type hint.
- Общий рефакторинг lowering, type inference или системы диагностики.

## Decisions

### 1. Специальная форма и нативное выражение

Обрабатывать `instance?` как специальную форму по аналогии с `cast`, до общего функционального вызова. Генерировать `(((Object) VALUE) instanceof TYPE)`. Cast к `Object` позволяет Java принять заведомо несовместимые статические типы, например строку при проверке `Integer`, и даёт boxing примитивных значений. `VALUE` встречается ровно один раз; отдельная временная переменная для самой проверки не нужна.

Обычная runtime-функция потребовала бы передачи Class-значения и не дала бы требуемый нативный `instanceof`. Прямая генерация `VALUE instanceof TYPE` не подходит для несовместимых final-классов и primitive expressions.

### 2. Имена классов разрешает javac

Использовать статический символ типа без вычисления как local/function value. Короткие имена разрешаются существующими Java imports и обычными правилами Java, полные имена передаются как имена типов. Не добавлять таблицу импортов в контекст только ради этой формы. Проверять форму, literal-операнды и primitive type names в генераторе, а существование, доступность и допустимость Java-типа оставить `javac`.

Ошибка на стадии `javac` считается compile-time ошибкой для #20. Это согласованный простой вариант; генератор исходника не получает classpath и не пытается дублировать проверку Java-компилятора.

### 3. Lowering сохраняет синтаксический операнд типа

Добавить узкую обработку `instance?`, которая сохраняет операнд типа, арность и metadata исходной формы, а нормализует только `value` корректной двухаргументной формы. Malformed формы не превращать в корректные до backend-диагностики. Иначе `(instance? (do String) value)` может ошибочно стать допустимым после общего lowering.

В discard-позиции сохранять вычисление результата через существующий механизм временного `let*` binding с именем от `Gensym`. Это необходимо, поскольку `instanceof` не является допустимым самостоятельным Java statement. Не перестраивать общую классификацию всех выражений ради одного оператора.

Уточнение после JDK-проверки: промежуточные выражения тела функции не проходят через `lower_discard`, а последняя форма void-лямбды определяется Java-аннотацией. Для этих путей Java-генератор также связывает отброшенный `instance?` с временным именем через `Gensym`. Общая функция генерации отброшенного выражения используется для промежуточных форм тела и последней формы void-лямбды; остальные формы сохраняют прежнюю генерацию statements. Оба пути проверяются исполнением на JDK.

### 4. Неподдерживаемые targets диагностируют форму явно

В JS generator отклонять `instance?` до общего вызова. В evaluator отклонять достигнутую форму до вычисления её аргументов. Это лучше случайного `symbol not found` или runtime `ReferenceError`; новые представления host-типов не нужны. Как и другие специальные формы, `instance?` не становится first-class функцией.

### 5. Проверка на JDK без Android

Добавить компактный целевой suite по образцу `test/get_in_test.ml`: компиляция исходника, запуск `javac` с `RUNTIME_JAVA`, Java runner с проверками и отдельный negative compile для отсутствующего класса. Зарегистрировать suite в `test/dune`. Использовать `ArrayList`, `AbstractList`, `List`, `String`, `Integer`, `Boolean`; single evaluation проверять счётчиком в atom. В том же suite проверить диагностику Java/eval/JS. Генерацию и lowering проверять точечно, используя существующие suites там, где это сокращает тест.

## Risks / Trade-offs

- Ошибка неизвестного класса появляется только при запуске `javac` → документировать разницу между генерацией исходника и Java compilation; проверять отказ настоящим `javac`.
- Общий lowering может скрыть неверный TYPE или создать недопустимый statement → проверки malformed операндов, управляющих выражений и discard-позиции обязательны.
- Статический тип `value` может запретить обычный Java `instanceof` → всегда приводить левую часть к `Object`, включая скаляры и `nil`.
- Новый специальный оператор занимает имя `instance?` в позиции формы → документировать его как Java-only форму, а не обычную функцию.

## Migration Plan

Миграция данных и runtime-библиотек не требуется. После полной проверки компилятора обновить английский справочник `skills/y2k-language/SKILL.md`. Существующий workaround `Class.isInstance` остаётся рабочим; переход приложений на новую форму добровольный. Откат изменения возвращает необходимость workaround для новых вызовов `instance?`.
