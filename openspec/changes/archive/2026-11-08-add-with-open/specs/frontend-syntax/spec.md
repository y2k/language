# Spec Delta

## ADDED Requirements

### Requirement: with-open SHALL последовательно связывать Java-ресурсы

Java SHALL поддерживать `(with-open [name expression ...] body...)` с простыми символьными именами без destructuring. Initializers SHALL вычисляться один раз слева направо, каждый в окружении предыдущих bindings. Исходные аннотации типов bindings SHALL сохраняться. Пустой вектор SHALL быть допустим.

#### Scenario: Зависимые ресурсы
- **WHEN** второй initializer использует первый ресурс
- **THEN** он видит binding первого ресурса, а каждый initializer выполняется ровно один раз в исходном порядке

#### Scenario: Сохранение подсказки типа
- **WHEN** binding ресурса имеет аннотацию `^java.io.Reader`
- **THEN** тело может вызывать методы `Reader` согласно существующим правилам Java interop

### Requirement: with-open SHALL сохранять значение тела

Тело `with-open` SHALL выполняться после успешного вычисления всех initializers и возвращать значение последней формы после успешного закрытия ресурсов. Пустое тело SHALL возвращать `nil`. Пустой вектор SHALL выполнять только тело. Форма SHALL работать в позиции значения и в позиции с отброшенным результатом.

#### Scenario: Несколько выражений и falsey-результаты
- **WHEN** тело содержит несколько выражений и завершается `false` либо `nil`
- **THEN** все выражения выполняются по порядку, а результат равен соответственно boolean `false` либо `nil`, не их строковому представлению

#### Scenario: Пустые формы
- **WHEN** выполняются `(with-open [] 42)` и `(with-open [])`
- **THEN** результаты равны соответственно `42` и `nil`

#### Scenario: Пустое тело с ресурсом
- **WHEN** `with-open` связывает ресурс, но не содержит форм тела
- **THEN** ресурс закрывается и возвращается `nil`

#### Scenario: Контексты использования
- **WHEN** `with-open` используется как аргумент функции либо как непоследняя форма тела
- **THEN** закрытие завершается перед следующим внешним вычислением, а значение передаётся или отбрасывается согласно позиции

### Requirement: with-open SHALL закрывать ресурсы через AutoCloseable

Каждый успешно связанный ресурс SHALL закрываться ровно один раз в обратном порядке через Java `AutoCloseable.close()`, включая исключительные выходы. Закрытие SHALL работать с результатом фабрики типа `Object` без подсказки типа. Для статического типа `Object` проверка интерфейса SHALL происходить при закрытии через cast. `nil` SHALL NOT пропускаться; статически несовместимый тип допускает ошибку компиляции Java.

#### Scenario: Фабрика возвращает Object
- **WHEN** языковая функция возвращает объект `AutoCloseable`, который связывается без аннотации типа
- **THEN** `with-open` компилируется для Java и вызывает его `close()`

#### Scenario: Обычный выход
- **WHEN** открываются ресурсы `a` и `b`, затем тело успешно завершается
- **THEN** журнал действий содержит открытие `a`, открытие `b`, тело, закрытие `b`, закрытие `a`

#### Scenario: Ошибка следующего initializer
- **WHEN** открытие `a` успешно, а initializer `b` выбрасывает исключение
- **THEN** тело не выполняется, закрывается только `a`, и при успешном закрытии распространяется исходное исключение

#### Scenario: Ошибка тела
- **WHEN** тело выбрасывает исключение, а закрытия успешны
- **THEN** все ресурсы закрываются в обратном порядке и распространяется тот же объект исключения

#### Scenario: Неподходящий ресурс со статическим типом Object
- **WHEN** binding получает результат фабрики типа `Object`, который не реализует `AutoCloseable`
- **THEN** тело выполняется, а при закрытии возникает `ClassCastException`
- **AND** внешние ресурсы всё равно проходят закрытие

#### Scenario: Статически несовместимый тип
- **WHEN** тип binding не допускает Java-приведение к `AutoCloseable`, например `String`
- **THEN** допускается ошибка компиляции Java

#### Scenario: Nil-ресурс
- **WHEN** binding получает `nil`
- **THEN** тело выполняется, а при закрытии возникает `NullPointerException`
- **AND** внешние ресурсы всё равно проходят закрытие

### Requirement: Ошибки закрытия with-open SHALL следовать семантике finally

Ошибка закрытия SHALL заменять текущий результат или исключение без автоматического добавления suppressed exceptions. Ошибка внутреннего закрытия SHALL NOT препятствовать закрытию внешних ресурсов. Если внешнее закрытие тоже завершается ошибкой, SHALL распространяться ошибка внешнего закрытия.

#### Scenario: Ошибка тела и внутреннего закрытия
- **WHEN** тело выбрасывает `body-error`, закрытие `b` выбрасывает `close-b-error`, а закрытие `a` успешно
- **THEN** закрытие `a` выполняется и распространяется `close-b-error` без автоматически добавленного `body-error` в suppressed exceptions

#### Scenario: Ошибки обоих закрытий
- **WHEN** закрытия `b` и затем `a` выбрасывают разные исключения
- **THEN** распространяется исключение закрытия `a`
