# Design

## Context

Мотивация — в `proposal.md`. Изменение пересекает несколько runtimes и требует решения о представлении результатов, поэтому design необходим.

`backend_eval/eval_stdlib.ml` использует общий `to_int` в арифметике и сравнениях; `/` также использует целочисленную свёртку. Значения eval представлены `Symbol of string`, и `=` сравнивает их текст. В Java `prelude/language_runtime.java` использует `intValue()` и возвращает `Integer`; равенство реализовано через `Objects.equals`. JS уже вычисляет дробные `+`, `-`, `*`, но `Object.is` различает нули разных знаков. Java и JS generators выводят дробные литералы без числовой обёртки.

`test/test.ml` автоматически запускает общие samples на трёх targets, включая Node и настоящую компиляцию `javac`/запуск JVM. Существующий `plus.clj` проверяет только целочисленные `6 5 24 4`.

Уточнение после реализации: `prelude/language_runtime.java` и `.js` — отслеживаемые симлинки в `/Users/igor/Projects/packages/prelude/1.0.0/java/language_runtime.java` и `js/language_runtime.js`. Пользователь явно разрешил включить оба реальных файла репозитория `packages` в объём change. Проверка `make test` выполнялась с этими обновлёнными runtime-файлами.

## Goals / Non-Goals

**Goals:**
- Реализовать контракт `specs/fractional-arithmetic/spec.md` небольшими изменениями runtime, сохранив текущий frontend и harness.
- Нормализовать именно результаты трёх операций, чтобы согласовать их вывод и сравнение с целыми без полной реформы типов eval.
- Не терять binary64-точность при передаче результата следующей операции через текстовое значение eval.

**Non-Goals:**
- Менять общий `to_int` так, чтобы случайно расширить `/`, сравнения, индексы или `drop`.
- Вводить decimal, BigInt, новый публичный числовой тип либо новую зависимость.
- Обещать одинаковый текст любого числа вне явно заданных сценариев или исправлять все различия равенства исходных литералов, строк и коллекций.

## Decisions

### 1. Две ветки арифметики в eval и Java

Для вызова только с целыми аргументами сохранить существующий целочисленный путь. При дробном аргументе выбрать binary64-путь для всего вызова и выполнить левую свёртку без промежуточного форматирования. Это сохраняет целочисленную совместимость и не допускает потери дроби в начальном аргументе вычитания или позднем аргументе умножения. JS использует существующие операции `Number`.

Альтернатива — заменить все преобразования на float — затрагивает деление и сравнения и способна изменить точность больших целых. Она отвергнута. Для Java арифметические методы должны возвращать тип, допускающий `Integer` и `Double`, например `Number`; непосредственные Java-потребители старого return type потребуют перекомпиляции.

### 2. Нормализация результата вместо глобального изменения равенства

Точное целое в signed 32-bit диапазоне возвращать как обычное целое: `Integer` в Java, канонический десятичный `Symbol` в eval. В Java использовать явные ветви возврата: смешанный числовой тернарный оператор может выполнить promotion и снова вернуть boxed `Double`. Нулевой результат, включая отрицательный ноль, возвращать как положительный `0` на всех targets; в JS нормализация нужна в точках возврата этих трёх операций.

Так существующие `str`, `=` и `not=` уже обеспечат согласованные `"1"`, `true`, `false` для целых результатов дробных операций. Изменять глобальный `equal_value` для числоподобных строк или `Objects.equals` для всех объектов не требуется. Это важная граница: eval не различает строку `"1"` и числовой текст, поэтому глобальный числовой fallback расширил бы семантику строк и коллекций.

### 3. Текст нецелого результата eval должен сохранять значение

Использовать стандартное форматирование OCaml и проверку round-trip через стандартный float parser. Небольшой helper может выбирать минимальную точность `%g` от 1 до 17 значащих цифр, при которой обратное чтение восстанавливает исходное конечное binary64-значение. Это даёт короткие `1.2` и `0.4` для issue и не теряет точность при вложенной арифметике. Не применять фиксированное малое число знаков после точки или epsilon-округление до целого.

Java и JS сохраняют нативное форматирование нецелых значений. Полный алгоритм идентичной печати всех binary64 на трёх targets не нужен: контракт фиксирует обычные примеры и нормализацию целых, а не сериализацию чисел. Ограничение межцелевого форматирования экспоненты следует обозначить в документации; если helper сознательно не решает его, комментарий `ponytail:` должен назвать предел и путь к общему formatter при появлении такой необходимости.

### 4. Общие samples плюс точечные проверки ошибок и точности

Добавить `test/samples/fractional_arithmetic.clj` с точно представимыми дробями `0.25`, `0.5`, `0.125`: дробные и смешанные аргументы, отрицательные результаты, несколько аргументов, вложенные операции и `reduce`. Отдельно включить реальные `0.2` из issue и проверки нормализации результатов каждой операции через `str`, `=` и `not=`. Проверить ноль от `(* -0.5 0)`.

Дополнить целочисленный sample граничными арностями и `(/ 7 2)` → `3`, чтобы случайное изменение деления обнаруживалось. Для `(-)` использовать существующий подход целевых тестов с ожидаемой ошибкой: общий sample runner рассчитан на успешное завершение. Для formatter eval добавить небольшую проверку round-trip на числе, которому недостаточно 12 значащих цифр; это проверяет реальную потерю точности, а не копирует алгоритм formatter.

Не помечать новые проверки как ожидаемо падающие и не отключать eval/Java: итогом change должны быть зелёные тесты на всех targets.

## Risks / Trade-offs

- [Потеря точности из-за строкового представления eval] → проверка round-trip и вычисления с результатом предыдущей операции.
- [Неожиданное изменение `/` и сравнений через общий helper] → отдельный путь для `+`, `-`, `*`, регрессионный пример целочисленного деления.
- [Изменение возвращаемого Java-типа] → явная запись в документации, перекомпиляция generated code вместе с обновлённым runtime.
- [Правки runtime не видны в diff репозитория language из-за симлинков] → проверять diff обоих репозиториев; runtime и compiler поставлять согласованно. Тесты читают реальные файлы prelude через симлинки.
- [Issue #22 шире change] → не заявлять исправление дробных сравнений и деления; оставить их открытыми вопросами.
- [Разные диапазоны целых и печать экспонент] → гарантировать согласованную нормализацию целых только в signed 32-bit диапазоне и документировать пределы.

## Migration Plan

После реализации обновить English reference `skills/y2k-language/SKILL.md`, отформатировать изменённые OCaml-файлы через `ocamlformat -i` и выполнить `make test`. Распространение исправления требует обновления Java/JS runtime вместе с соответствующей версией compiler; публикация пакетов не входит в задачи change. Данных для миграции нет. При откате вернуть compiler/runtime согласованной парой, учитывая возвращение ограничений дробной арифметики.
