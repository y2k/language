## Context

Мотивация описана в `proposal.md`. `frontend/builtin_macros.ml` уже сохраняет metadata имени метода, а `backend_compiler/java.ml` преобразует `^override` в `call_super`. Единственный генератор методов `compile_gen_method` безусловно выводит `@Override`, после чего независимо добавляет опциональный `super` и вызов helper.

Основная спецификация `compiler-targets` описывает общую генерацию вложенного класса, но не различает новые методы и переопределения. Delta добавляет эти гарантии, сохраняя существующий interop-контракт. Справочник `skills/y2k-language/SKILL.md` сейчас ограничивает поддержку словами «Only `void` overrides are supported».

Design фиксирует решение неоднозначности между аннотацией и вызовом предка, а также способ проверить launcher независимо от обычных method calls. Согласовано полное удаление `@Override`.

## Goals / Non-Goals

**Goals:**
- Исправить общий путь генерации, сохранив сигнатуры, передачу `this`, порядок аргументов, вызов `super` и обработку исключений.
- Проверять наблюдаемое исполнение, включая динамическую диспетчеризацию и порядок эффектов.

**Non-Goals:**
- Анализировать classpath или определять в OCaml, какие методы существуют у предка.
- Добавлять metadata для обязательного переопределения, static methods или non-void results.
- Менять общую модель классов и создавать отдельный launcher для приложений.

## Decisions

### Удалить аннотацию, оставить Java правила переопределения

Убрать элемент `"@Override"` из результата `compile_gen_method`. Оставить `parse_gen_class`, `call_super`, вызов helper и обработку исключений без семантических изменений. Java определяет переопределение по сигнатуре и наследованию; аннотация не нужна для диспетчеризации.

Рассмотренные альтернативы: выводить аннотацию только при `^override` либо добавить отдельную metadata. Первая не обеспечивает проверку намерения у переопределений без `super`, вторая расширяет синтаксис сверх потребности issue. Автоматическое определение методов предка требует лишней интеграции с Java classpath. Полное удаление согласовано с пользователем.

### Проверять эффекты через существующую тестовую инфраструктуру

В `test/java_ns_test.ml` обновить snapshot Android `onCreate`: аннотации нет, `super.onCreate(arg0)` по-прежнему предшествует helper. Добавить компактные проверки нового метода и сохранения отказа для non-void результата.

Java sample fixtures должны вызывать новые методы и проверять аргументы/получателя. Для переопределений использовать стандартный конкретный предок с наблюдаемым эффектом, например `java.util.ArrayList.clear`: заполнить список, вызвать `clear` через тип предка и наблюдать размер из helper. Без metadata helper видит исходное содержимое; с `^override` — уже пустой список. Вывод helper позволяет проверить однократность его выполнения. Это обходится без Android SDK и нового тестового Java-предка. Существующий `gen_class_thread.clj` вызывает только `interrupt` и `isAlive`, поэтому не заменяет эту проверку.

Для нового метода с `^override` сохранить реальный отказ `javac` на отсутствующем `super.main()`. Не вводить свою проверку доступности методов.

### Проверять instance entry point отдельным запуском JDK 25

`test/test.ml:run_java` сейчас всегда генерирует статический `TestRunner`, поэтому его обычный вызов не доказывает launcher-контракт. Добавить небольшой целевой тест в существующую Java-инфраструктуру: скомпилировать source из сценария спецификации вместе с runtime и запустить `java -cp out checks.entry$Runner` напрямую через массив аргументов процесса. Переиспользовать существующие функции запуска команд и подготовки generated source, без универсального framework для entry points.

Запуск на JDK 25 — обязательная проверка при приёмке; отсутствие подходящего JDK не считать успехом этого сценария. Локально при исследовании доступен JDK 25.0.1. Не добавлять флаги preview и не делать Java 25 условием самой генерации обычных instance methods.

## Risks / Trade-offs

- [Опечатка в имени предполагаемого переопределения может стать новым методом] → Документировать, что `^override` управляет вызовом предка, а отдельной проверки намерения нет. Если такая потребность появится, отдельно спроектировать metadata; не добавлять её в это исправление.
- [Проверка через статическую обёртку скрывает дефект прямого запуска] → Отдельно запускать binary name `checks.entry$Runner` на JDK 25 и проверять вывод и exit code.
- [Snapshot не доказывает порядок исполнения] → Проверить эффект конкретного метода предка, видимый из helper, и диспетчеризацию через тип предка.

## Migration Plan

Миграция пользовательских исходников не нужна. Перегенерировать Java после обновления компилятора; существующие объявления и metadata сохраняются. Обновить справочник одновременно с реализацией. Откат изменения генератора вернёт прежнее ограничение на новые методы; изменений данных или runtime нет.
