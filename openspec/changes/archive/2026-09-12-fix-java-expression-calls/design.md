## Context

Мотивация описана в `proposal.md`. `compile_expr` в `backend_compiler/java.ml` различает локальный символ, нелокальный символ и выражение в позиции вызова. Только локальный символ проходит через `fn_interface`; выражение получает голый `.call(...)`. Top-level методы и `Fn0`–`Fn4` возвращают `Object`.

Проверка текущего CLI и `javac` подтвердила ошибку для фабрики, callback-цепочки, `get` и `if`. Непосредственная лямбда, явный `cast Fn1` и локальный binding скомпилировались и вернули `"ok"`. Lowering иногда превращает результат `let` в локальный символ, но результат `if` остаётся вызовом `Supplier<Object>.get()`.

Короткий design фиксирует выбор между приведением в генераторе и нормализацией вызовов в lowering, а также границу совместимости с Java interop.

## Goals / Non-Goals

**Goals:**
- Восстанавливать интерфейс вызова там, где известна арность применения, независимо от формы возвращающего функцию выражения.
- Использовать существующую диагностику арности и metadata внешнего вызова.

**Non-Goals:**
- Вывод возвращаемых Java-типов, новые runtime-интерфейсы и поддержка арностей выше четырёх.
- Автоматическая адаптация произвольных Java SAM-интерфейсов к функциям языка; `Function.apply` и аналогичные методы остаются Java interop.
- Изменение разрешения нелокальных символов или общая переработка порядка вычисления в lowering.

## Decisions

1. **Приведение в общей ветке вызова выражения.** Генерировать `((FnN) <compiled-expression>).call(<args>)`, используя `fn_interface` и количество аргументов внешнего вызова. Это общий путь для всех подтверждённых случаев. Альтернатива — выносить вызываемое выражение в локальный binding через lowering — затрагивает общий для JS и Java слой и требует лишних временных имён.

2. **Повторно использовать helper, без нового диспетчера.** Сохранять metadata внешнего `SList`, а для имени без символьного обозначения передавать helper стабильное описание `expression`. Существующий helper обеспечивает предел 0–4 и координаты. Новый runtime-диспетчер дублировал бы уже имеющуюся стратегию локальных вызовов.

3. **Безусловный внешний cast без анализа типов выражения.** Выражение включается в результат ровно один раз. Правило применяется и к непосредственной лямбде, и к любому `(cast TYPE ...)`; исключений по AST или указанному Java-типу нет. Повторный cast для лямбды или `(cast FnN ...)` допустим. Пояснить сознательное повторное приведение коротким комментарием `ponytail:` рядом с генерацией. Принятое ограничение совместимости: объект с произвольным методом `call`, не реализующий соответствующий `FnN`, вызывается через `(.call (cast TYPE value) args...)`, а не через функциональный синтаксис.

4. **Проверять исполнение через существующий sample runner.** Один общий sample объединяет фабрики арностей 0–4, callback-цепочку, `get`, `if` и счётчик вызовов фабрики через atom. В sample включить локальный вызов и непосредственную лямбду как контрольные случаи. Явный `cast FnN` проверить в Java-целевом sample, поскольку это Java interop. Неподдерживаемую арность проверять в существующем `test/java_ns_test.ml` с арностью и координатами внешней формы; snapshot всего Java-класса не нужен.

5. **Однократность отдельно от порядка эффектов.** Lowering может вынести эффект из аргумента перед вычислением фабрики, например в `((factory) (do (effect) value))`. Исправление этого порядка выходит за scope #19. Совпадение с eval гарантируется для перечисленных в delta spec сценариев; их аргументы не создают конкурирующих эффектов. Atom-счётчик проверяет число вычислений фабрики, а не её положение относительно эффектов аргументов.

6. **Проверить границу Java interop.** В существующем целевом тесте генерации проверить, что `((cast java.util.concurrent.Callable x))` получает внешний `Fn0`, а `(.call (cast java.util.concurrent.Callable x))` остаётся прямым Java-вызовом. В Java-целевом sample выполнить явный `.call` на типизированной `Callable`-лямбде. Это проверяет принятое правило стандартным Java-интерфейсом без новых вспомогательных классов.

## Risks / Trade-offs

- Неверное функциональное значение или несовпадение его фактической арности с вызовом приведёт к ошибке Java-типа либо runtime cast, как и для локальных функций. Контракт гарантирует успешный вызов только корректного значения соответствующей арности.
- Существующие inline-лямбды и явные casts получат дополнительное приведение → регрессия проверяет их реальную компиляцию и исполнение.
- Прежний вызов `((cast CustomType value) args...)` может перестать работать, если объект не реализует `FnN` → это принятое ограничение; для Java-метода использовать явную форму `(.call ...)`.
- Проверка лишь текста Java не обнаружит всех ошибок типов → общие и Java-целевые samples проходят через `javac` и `java`.

## Migration Plan

Выпустить исправленный компилятор после `make test` и пересобрать потребляющее приложение. Обходные casts к `FnN` можно сохранить или удалить после обновления. Вызовы произвольного Java `call` через функциональный синтаксис перевести на явный `(.call ...)`. Миграция runtime и данных не нужна; откат — возврат предыдущей версии компилятора и сохранение обходных casts к `FnN`.
