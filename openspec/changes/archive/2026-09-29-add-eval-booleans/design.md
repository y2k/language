# Design

## Context

См. `proposal.md` о мотивации. `eval_types.ml` уже содержит отдельный `Nil`, но boolean остаются `Symbol "true"`/`Symbol "false"`. Их создают lookup литералов, `quote`, `=`, `not`, `assert`, `vector?` и числовые сравнения. Проверка ложности дублируется в `eval.ml` и stdlib. Runner печатает только `Symbol` и `Nil`; тестовый helper `last_symbol` предполагает текстовое представление даже результата предиката.

Main spec отстаёт: `add-eval-nil` и `add-atoms` реализованы, но не синхронизированы. Delta сохраняет имена требований текущей main spec, включая историческое название runner, и включает сценарии nil из завершённого change. При последующей синхронизации нужно учесть переименование runner в `add-eval-nil` и не применять старые deltas поверх новых. Ни main specs, ни старые changes в рамках создания этих артефактов не редактируются.

## Goals / Non-Goals

**Goals:** одно представление boolean у всех производителей и одна проверка истинности; каждый промежуточный change самостоятельно собирается и проходит suites.

**Non-Goals:** разделение остальных скаляров, изменение порядка lookup, арностей, равенства функций/Atom, реализации JS/Java и раскрытия макросов.

## Decisions

### 1. Добавить `Bool of bool`

Новый конструктор в `eval_types.ml` отличает boolean от текста без специальных строковых маркеров. Альтернатива — особая обработка строк в `if` — не исправляет равенство и не сохраняет тип при передаче через функции.

В `find` распознавать boolean там же, где сейчас разрешаются литералы, после поиска bindings. В `quote` распознавать `true`/`false` без lookup и рекурсивно сохранять их в списках. Строковые атомы по-прежнему становятся `Symbol`.

### 2. Общая истинность и типизированные результаты

Поместить небольшой helper истинности в `eval_types.ml`, доступный eval и stdlib без циклических зависимостей. Только `Nil` и `Bool false` ложны. Использовать его в `if`, `not`, `assert`; предикаты и сравнения возвращают `Bool`. Раскрытые `and`, `or`, `cond`, `if-let` автоматически получают новую семантику через `if`.

`equal_value` получает ветку boolean; межтиповое равенство остаётся ложным. Текущий поиск ключей различает конструкторы, поэтому boolean и текст разделяются и там. Полная унификация поиска ключей с языковым равенством выполняется во втором change, когда появляется смешанное числовое равенство.

### 3. Вывод и диагностика адаптируются вместе с моделью

Добавить boolean в `to_string`, `value_text` и scalar-ветку runner. Не использовать общий `to_string` для всех финальных значений: списки, map, функции и Atom по-прежнему не выводятся runner автоматически. Диагностика вызова boolean как функции должна называть boolean, а не symbol.

### 4. Тестировать значение, а не только вывод

Общие samples проверяют истинность `"false"`, `not`, бинарное равенство и управляющие макросы через `str`. Eval-only fixtures покрывают quoted boolean, map keys, деструктуризацию и round-trip через Atom. В `test/eval_ns_test.ml` добавить проверки `Bool` и обновить устаревшие ожидания ложности `"false"`; helpers для текстового вывода не заменяют проверки runtime-конструкторов.

## Risks / Trade-offs

- Пропущенный производитель boolean вернёт строку, которая теперь истинна → проверить все `Symbol "true"`/`Symbol "false"` и результаты stdlib.
- Существующие eval-программы полагаются на ложность `"false"` → описать breaking change; для проверки текста использовать `(= value "false")`.
- Совпадение вывода скрывает смешение типов → тестировать конструкторы, равенство и map keys.
- Несогласованные старые deltas могут вернуть предыдущую истинность → согласовывать specs последовательно: завершённые nil/Atom, boolean, скаляры, контракты; при rebase сохранять все scenario names.

## Migration Plan

Внести модель, производителей, потребителей и тесты одной реализацией change; обновить английский справочник и выполнить `make test`. Данные runtime не сериализуются, миграции хранилища нет. При откате вернуть весь change вместе с документацией и тестами; последующие changes требуют этой модели и откатываются раньше него.

### Согласованный baseline для последующей синхронизации

На момент реализации main spec ещё использует `The eval target SHALL return only the final symbol value`; данный delta адресует именно это существующее требование. Синхронизация/архивация старых changes — отдельная операция, а не часть реализации boolean.

| Область | Как сохранить согласованный результат |
| --- | --- |
| Runner | Если сначала синхронизирован `add-eval-nil`, он переименует требование в `The eval target SHALL return the final symbol or nil value`. Перед синхронизацией boolean заменить только адресующий заголовок его MODIFIED-блока на это имя; сценарии `Evaluate sample test function`, `Non-symbol final result`, `Eval error result`, `Финальное nil` и `Финальный boolean` сохраняются. |
| Literal lookup, quote и control | Boolean-delta уже включает nil-сценарии `Литерал nil`, `Загрузка зависимостей`, `Цитирование вложенного nil` и обновляет только boolean-семантику. Применять его после nil-delta, а не наоборот. |
| Stdlib и Atom | Boolean-delta не заменяет stdlib requirement. При отдельной синхронизации `add-atoms` объединить его Atom bindings/scenario с текущим main-блоком, сохранив `get-in`, `Get from nil` и остальные текущие сценарии: старый Atom-блок не является полной актуальной заменой. |
| Отдельные требования | Сохранить `Eval SHALL отличать nil от текстового значения во всех операциях`, capability `atoms` и текущий get-in contract; boolean-добавление их не удаляет. |

Следующие scalar/contracts changes синхронизируются после boolean и выполняют свой предусмотренный rebase заголовка runner. Эта последовательность не требует отката реализованного nil/Atom или изменений их исходных артефактов при применении boolean.
