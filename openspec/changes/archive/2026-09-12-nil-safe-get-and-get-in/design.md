## Context

Мотивация описана в `proposal.md`, контракт — в двух delta specs. Изменение пересекает evaluator, два runtime и JS import, поэтому требует общего design.

Текущий `get` в `backend_eval/eval_stdlib.ml` и `prelude/language_runtime.{js,java}` принимает коллекции, но отклоняет `nil`. `frontend/builtin_macros.ml` уже раскрывает keyword lookup в `get`. Вектор раскрывается в `list`; evaluator хранит его как `List`, JS — array, Java — `java.util.List`. Различия между list и vector к runtime не сохраняются.

`backend_compiler/js.ml` перечисляет импортируемые функции явно, Java использует static wildcard import. В `test/test.ml` общие sample files автоматически запускаются на eval, JS и Java; ошибки внешних процессов обрабатываются как провал теста, поэтому негативные сценарии требуют целевых проверок, а не обычного общего fixture с ожидаемым текстом ошибки.

Основная спецификация evaluator содержит закрытый перечень stdlib (`exactly`), уже расходящийся с кодом, где есть `assert` и atoms. Delta сохраняет все старые сценарии, добавляет `get-in` и делает перечень совместимым с bindings из других требований. Это не задача на переописание всех существующих stdlib функций.

## Goals / Non-Goals

**Goals:**
- Одна семантика lookup на каждом backend: прямой `get`, keyword lookup и шаг `get-in` используют общий `get`.
- Реализация через существующие контейнеры и стандартную последовательную свёртку, без новых зависимостей.
- Проверяемое различие между отсутствием значения и неверным типом коллекции или пути.

**Non-Goals:**
- Новое представление vector/list, literal-only макрос пути или новая инфраструктура регистрации builtins.
- Унификация текстов исключений и неподдерживаемых индексов.
- Изменение evaluator bindings ради nil-безопасного destructuring.

## Decisions

### 1. Nil-защита находится в общем get

Добавить случай runtime `nil` перед существующей обработкой коллекций. Сохранить текущие ветви map/list и ошибки скалярных коллекций. В JS сохранить нормализацию прочитанного `undefined` через `?? null`, не заменять её на truthiness или `||`.

Альтернатива — отдельная защита в keyword macro или `get-in` — оставила бы прямые вызовы `get` с другой семантикой и дублировала логику.

### 2. get-in — обычная runtime-функция

После проверки типа пути выполнить left fold с исходным `collection` как аккумулятором и общим `get` на каждом шаге. OCaml использует `List.fold_left`, JS — array reduce, Java — короткий цикл по `java.util.List<?>`. Не нужна отдельная проверка truthiness аккумулятора: `get(nil, key)` уже возвращает `nil`, а скалярный аккумулятор должен вызвать ошибку, если шаги ещё остались.

Проверка типа пути выполняется до обхода, включая случай исходного `nil`. Пустой путь возвращает исходное значение без чтений и копирования. Обе формы аргументов вычисляются обычным механизмом вызова функции, а не макросом, который мог бы дублировать выражения.

Зарегистрировать `get-in` в evaluator, экспортировать `get_in` в runtimes и добавить его в JS import. Существующее munging преобразует дефис в подчёркивание; Java не требует нового реестра. Альтернатива с macro expansion усложнила бы поддержку динамического пути.

### 3. Гарантируется vector, list остаётся неспецифицированным

Проверять существующий runtime sequence type. Он принимает и list, но дополнительный код для различения, поддержки или запрета list не добавляется. UB здесь означает отсутствие гарантии языка, а не требование вызвать ошибку. Не писать тесты, закрепляющие поведение list-пути. `nil`, map, строка, число и boolean как путь отклоняются.

Альтернатива со специальным vector tag затрагивает frontend, quote, predicates и все runtime; это несоразмерно lookup API. Проверка только литерала исключила бы векторы из переменных и функций.

### 4. Проверки следуют существующему test harness

Добавить общий fixture для всех примеров #17, пути из переменной/функции, пропущенного индекса, сохранения false и регрессий обычного `get`. Для пустого пути с map проверить результат через последующий lookup или строковое представление: JS `=` сравнивает объекты по identity, поэтому сравнение с новой map не является переносимым тестом.

В существующем формате целевых OCaml/Alcotest тестов проверить ошибки скалярного промежуточного значения и неверного типа пути на всех трёх backend, без фиксации общего текста исключений. Отдельно проверить JS object с отсутствующим свойством и явным `undefined`, а также сохранение `false`, `0`, `""`. Переиспользовать имеющиеся способы запуска runtime, не создавать новый тестовый framework. Полная проверка — `make test`.

## Risks / Trade-offs

- [Compiled destructuring также использует `get`] → После изменения `(let [{:chat {:id id}} {}] id)` сможет вернуть `nil` в JS/Java, тогда как `backend_eval/eval.ml` продолжит отклонять вложенный pattern на `nil`. По согласованной границе этот случай не получает общего контракта и не включается в acceptance данного change.
- [Некорректные индексы уже различаются между backend] → Гарантии ограничены неотрицательными целыми индексами, включая выход за границу; отрицательные и нечисловые индексы не унифицируются.
- [List-путь может случайно стать обещанной возможностью] → В спецификациях он явно не определён; не добавлять специальные ветви или acceptance-тесты для него.
- [JS принимает обычные interop objects] → Сохранить текущую ветвь object lookup и проверить нормализацию `undefined`; не подменять общий `get` произвольным optional property access для всех типов.

## Migration Plan

При реализации обнаружено, что `prelude/language_runtime.{js,java}` — отслеживаемые Git символические ссылки на соседний репозиторий `packages`, каталог `prelude/1.0.0/{js,java}`. Изменения runtime сохранены там в коммите `c71906ab7fb9104df0ee9bf4c853edb2b19d9533` (`prelude: add atoms and get-in runtime helpers`); поставка этого change включает публикацию данного коммита вместе с изменениями `language`. Локальные `make test` и `git diff --check` прошли.

Миграция данных не требуется. Выпустить compiler и runtime вместе, поскольку новый JS import требует runtime с `get_in`. После форматирования изменённых OCaml файлов и успешного `make test` изменение готово к использованию потребителями. Откат выполняется согласованным возвратом compiler/runtime; исходники потребителей с `get-in` требуют версии, в которой эта функция доступна.
