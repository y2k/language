# Design

## Context

Мотивация — в [proposal.md](proposal.md); контракт — в [specs/internal-language-macros/spec.md](specs/internal-language-macros/spec.md). Подготовительный pipeline уже интегрирован коммитом `d59c64b`.

`Backend_eval.Pipeline` создаёт фабрики на каждый исходник под `Gensym.run`, добавляет их обработчики перед `Frontend.Desugar.builtin_macros` и передаёт конфигурацию в `Eval.context.parse_source`. Все прикладные callers уже используют этот API. `Frontend` не зависит от evaluator; загрузка пакетов не требует обратной зависимости `Eval -> Pipeline`.

Сейчас `cond_macro` в `frontend/builtin_macros.ml` строит вложенные `if`, а evaluator не имеет значения, сохраняющего AST и metadata. Spike проверил перенос с непрозрачным `Syntax`, включая Java-аннотации, JS source maps и вложенные пакеты. Его код используется как исследовательский материал, а не переносится целиком.

## Goals / Non-Goals

**Goals:** выполнить алгоритм `cond` существующим evaluator; сохранить исходные узлы; использовать готовые lifecycle и callback; поставлять самодостаточный executable.

**Non-Goals:** новый интерпретатор, дополнительные проходы AST, пользовательский `defmacro`, introspection для `Syntax`, syntax-quote, гигиена, перенос других макросов, глобальный cache, CLI-переключатель и исключение расширения из линковки. Новая система ошибок не требуется.

## Decisions

### 1. Непрозрачные исходные формы

В `Eval_types.value` добавить `Syntax of Frontend.sexpr`. Адаптер передаёт единственный аргумент `List [Syntax condition; Syntax result; ...]`, без имени `cond`. Это обычный список evaluator, поэтому подходят существующие `get`, `drop`, `list` и сравнение с пустым списком.

Содержимое `Syntax` не вычисляется и не разбирается языковыми функциями. `quote`, чтение литералов, отсутствующие значения и destructuring сохраняют прежнее поведение и не создают `Syntax`. Оно появляется только в адаптере. Полный узел надёжнее боковой таблицы или обратного преобразования обычного значения: одинаковые литералы могут иметь разные позиции и аннотации.

При расширении variant проверить exhaustive matches и потребителей: `Eval.value_text`, `Eval_stdlib.to_string`, равенство, truthiness, контейнеры и runner. Для диагностического текста достаточно непрозрачного маркера `#<syntax>`; truthiness остаётся общей (ложны только `Nil` и `Bool false`). Не вводить структурное сравнение содержимого `Syntax` или доступ к нему из языка. Существующие общие ветви неподдерживаемых значений и равенства переиспользуются. Входные формы могут лежать в списках и извлекаться без преобразования.

### 2. Обратный мост в модуле расширения

Добавить `backend_eval/language_macros.ml` с преобразованием результата:

| Значение evaluator | AST |
| --- | --- |
| `Syntax source` | исходный узел целиком |
| `List items` | круглая `SList`, рекурсивно преобразованные элементы |
| `Symbol name` | символьный atom |
| `Nil`, `Bool`, `Int`, `Float` | соответствующий literal atom |
| `String text` | строковый atom с уже декодированным содержимым |

Все новые узлы получают metadata вызова; `Syntax` сохраняет исходные metadata. Строки не проходят повторный парсинг или экранирование: AST хранит декодированное содержимое внутри внешних кавычек. Проверить кавычку, обратный слеш и LF прямым тестом моста.

`float_text` пригоден для представления значения, но печатает `1.0` как `1`. Если текст распознаётся как целое, добавить `.0`, чтобы сохранить категорию `Float`. Проверять не только печать результата, но и runtime-конструктор после eval полученного AST.

Неподдерживаемые результаты (например, closure или Atom) отклоняются существующим `Eval_error`; отдельный предварительный валидатор не нужен. Мост остаётся локальным для внутренних макросов, а не универсальным сериализатором runtime.

### 3. Bootstrap и определение cond

Хранить алгоритм в `backend_eval/macros/cond.clj` как внутреннюю функцию `expand-cond`, принимающую список clauses. Пустой список возвращает `nil`; иначе функция строит `(list 'if first-test first-result recursive-rest)`. Проверка пустоты через `(= clauses (list))` избегает повторного `count` всего остатка, замеченного в spike. Нового builtin не требуется.

В `backend_eval/dune` добавить правило, создающее `builtin_macro_source.ml` с OCaml raw-string из `%{read:macros/cond.clj}`. Исходник является build dependency; смена `.clj` вызывает перегенерацию. Runtime не читает `.clj` с диска.

Фабрика `Language_macros.create` создаёт новый `Eval.create_context ()`, разбирает встроенное определение низкоуровневым `Frontend.parse_and_desugar`, исполняет его и получает функцию `expand-cond`. Bootstrap использует оставшиеся OCaml-макросы и не вызывает полный pipeline, поэтому нет рекурсии инициализации. Отдельное окружение исключает доступ к пользовательским globals и утечку внутренних имён.

Обработчик узнаёт `(cond ...)`, проверяет чётность clauses с прежним `Failure "cond: expected test/result pairs"`, вызывает `Eval.apply_value` с обёрнутыми аргументами и преобразует результат в AST. Построение вложенных `if` находится только в `.clj`; OCaml fallback отсутствует. Существующий desugar затем обрабатывает результат и его детей, в том числе вложенные `cond`, коллекции и аннотации. Предварительная нормализация аргументов не нужна.

### 4. Стандартная композиция и отключение

Default `Pipeline.parse_and_desugar` становится `[Language_macros.create]`. `Pipeline.create_context` продолжает передавать ту же выбранную конфигурацию через callback. Явный `~extensions` заменяет default, как и сейчас: чтобы совместить своё расширение и языковое, caller включает обе фабрики. `~extensions:[]` оставляет только OCaml-макросы, в которых `cond` уже отсутствует.

Удалить `cond_macro` и его запись в списке `frontend/builtin_macros.ml`. Низкоуровневый frontend остаётся bootstrap/core API; он больше не обещает полного раскрытия `cond`. Изменения в backend-генераторах и обработке `deps` не требуются.

Текущие generic pipeline-тесты используют `cond` как пример встроенного OCaml-макроса. Перевести этот пример на оставшийся OCaml-макрос (например, `case`), сохранив проверку повторного раскрытия и порядка обработчиков. Отдельно проверить default/disabled поведение языкового `cond`, включая независимые вызовы и пакетный callback.

### 5. Ошибки и документация

Оставить существующие исключения и сообщения. Ошибка bootstrap-парсинга преобразуется в `Eval_error`, как в загрузчике пакетов; не добавлять контекстные обёртки, префиксы и новый протокол диагностики. Существующая проверка неполных пар остаётся в адаптере. Расширять границу перехвата runner только если интеграция реально потребует возврата `Error message`, используя уже существующее преобразование.

В английском `skills/y2k-language/SKILL.md` кратко уточнить автоматическую доступность внутреннего `cond` и отсутствие пользовательского macro API. Семантика таблицы `cond` сохраняется. Не описывать `Syntax` как пользовательский тип или форму.

## Risks / Trade-offs

- **Потеря annotations или loc** → прямые проверки исходных узлов и новых metadata, Java lambda fixture и JS source-map test.
- **Повторное вычисление пользовательских форм** → общие samples с эффектами, непроходимыми ветвями и вложенными коллекциями; вход передаётся только как `Syntax`.
- **Утечка compile-time состояния** → фабрика на файл; прямой тест двух фабрик, пользовательского одноимённого binding и файлов вложенных пакетов.
- **Скрытый fallback** → проверка `extensions:[]` оставляет `cond` нераскрытым; проверка исходников подтверждает удаление старого алгоритма.
- **Изменение категории чисел или текста в мосте** → unit-тесты по конструкторам, а не только строковому выводу.
- **Стоимость bootstrap и глубина рекурсии** → не кешировать окружение ради преждевременной оптимизации. Spike прошёл 5000 пар, но этот этап не обещает новую границу глубины или производительности.
- **Ограничения targets в fixtures** → не сравнивать списки по значению на JS; Java-результат `cond` при необходимости явно приводить к `Runnable`, как требует существующий backend.

## Migration Plan

1. Добавить внутренний тип, мост, встроенный исходник и фабрику; проверить их целевыми тестами.
2. Одной согласованной правкой включить фабрику по умолчанию, удалить OCaml `cond` и обновить ожидания generic pipeline-тестов.
3. Добавить интеграционные проверки, уточнить справочник, выполнить `make test` и строгую OpenSpec-валидацию.
4. Проверить executable из другого каталога без `LY2K_PACKAGES_DIR`: eval и генерацию JS для `(cond false 1 true 42)`, Java для `(defn test [] (cond false 1 true 42))`. Java требует функцию вокруг выражения верхнего уровня; это существующее ограничение target.

Исходники пользователей миграции не требуют. Откат атомарного change возвращает OCaml `cond` и пустой default расширений; подготовительный pipeline сохраняется.
