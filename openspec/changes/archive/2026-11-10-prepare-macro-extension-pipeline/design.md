# Design

## Context

Мотивация и границы этапа описаны в [proposal.md](proposal.md). Это сквозной рефакторинг frontend-вызовов, evaluator и runner, поэтому технический дизайн нужен, хотя delta specs отсутствуют.

Существующие точки:

- `Frontend.parse_and_desugar ?macros` разбирает исходник и вызывает `Desugar.desugar` внутри `Gensym.run`.
- `Desugar.macro` уже равен `sexpr -> sexpr option`. Переданный список заменяет встроенный; обработчики проверяются по порядку. После раскрытия результат обрабатывается снова, затем обходятся дети. `raw-code` защищён от обхода.
- `bin/runner.ml` раскрывает программу до выбора eval/JS/Java/FEX.
- `Eval.load_package_file` напрямую вызывает frontend при каждом `deps`. Загрузчик файлов уже инъецируется через effect handler; менять этот механизм не нужно.
- `backend_eval` зависит от `frontend`, но не наоборот. Runner и тесты уже зависят от обеих библиотек.
- [Spike](../../../../wayfinder/cond-mvp/assets/spike-results.md) проверил верхний pipeline, callback в eval-контексте и изоляцию расширений на полноценном переносе `cond`. Из spike берётся только подготовительная часть.

## Goals / Non-Goals

**Goals:**

- Одно место выбора дополнительных обработчиков для полного раскрытия программы и той же конфигурации при загрузке её пакетов.
- Подключение обработчика без изменения существующего обхода AST.
- Сохранение нынешнего результата, метаданных, порядка раскрытия и диагностики при стандартной конфигурации.
- Маленький рефакторинг, проверяемый независимо от будущей макросистемы.

**Non-Goals:**

- Выполнение макросов на языке, `Syntax`, преобразование runtime-значений в AST, bootstrap `.clj` и перенос `cond`.
- Новые стадии нормализации, система плагинов, глобальная регистрация, CLI-флаг отключения, полное исключение расширения из линковки.
- Новый протокол ошибок или диагностика некорректных расширений.

## Decisions

### 1. Верхний модуль в существующей библиотеке

Добавить `backend_eval/pipeline.ml`, доступный как `Backend_eval.Pipeline`. Он связывает frontend с созданием runtime-контекста, а позже сможет подключить фабрику языковых макросов без зависимости frontend от evaluator.

Минимальный внутренний API:

```ocaml
type extension = unit -> Frontend.Desugar.macro list

val parse_and_desugar :
  ?extensions:extension list -> string -> (Frontend.sexpr list, string) result

val create_context :
  ?extensions:extension list -> ?env:Eval.env -> unit -> Eval.context
```

В текущем этапе default extensions — пустой список. Сигнатуры описывают целевой интерфейс, а не новую отдельную иерархию объектов pipeline.

Альтернативы: новая библиотека и разделение frontend усложняют граф Dune без необходимости; размещение только в runner не покрывает загрузчик пакетов и прямые библиотечные вызовы. Общий mutable-реестр связывает независимые вызовы скрытым состоянием. Выбран модуль в существующей библиотеке, как проверено spike.

### 2. Композиция через существующий список макросов

Для каждого вызова полного раскрытия:

1. Вызвать переданные фабрики один раз в порядке списка.
2. Объединить возвращённые списки, сохранив порядок.
3. Добавить после них `Frontend.Desugar.builtin_macros` без изменения его порядка и состава.
4. Передать итоговый список в `Frontend.parse_and_desugar ~macros`.

Первое подходящее правило выигрывает согласно существующему `List.find_map`; отдельного диспетчера приоритетов нет. Это внутреннее соглашение композиции, а не обещание пользовательского переопределения макросов.

Фабрики и раскрытие выполняются под `Frontend.Gensym.run`. Вложенный вызов уже поддерживается реализацией `Gensym.run`; собственный генератор или сброс счётчика не нужны.

При `extensions:[]` поведение совпадает с прежним frontend. Отключение дополнительного тестового обработчика оставляет его форму нераскрытой; **`cond` на этом этапе продолжает раскрываться**, поскольку всё ещё находится в стандартном OCaml-списке.

Фабрики вызываются на каждый исходный файл, включая файлы `deps`, а не на каждый узел. Их состояние не кешируется между файлами или вызовами. Проверки фабрик, циклов раскрытия и произвольных пользовательских конфигураций не добавляются.

Альтернатива — передавать готовые обработчики с разделяемым состоянием. Фабрики выбраны потому, что следующий этап требует независимого compile-time окружения на файл; данный этап проверяет этот жизненный цикл обычной OCaml-closure.

### 3. Callback в eval-контексте

В `Eval.context` добавить:

```ocaml
parse_source : string -> (sexpr list, string) result
```

`Eval.create_context` принимает необязательный `~parse_source`. Его default сохраняет прежнее поведение через `fun source -> Frontend.parse_and_desugar source`; явная обёртка не даёт необязательному `?macros` попасть в тип callback.

`Pipeline.create_context ~extensions` передаёт callback `Pipeline.parse_and_desugar ~extensions` и сохраняет поддержку `?env`. `with_env` уже копирует record с заменой только окружения; новый callback должен сохраняться при таких переходах.

`Eval.load_package_file` вызывает `context.parse_source`, затем исполняет результат в том же runtime-контексте. Не меняются порядок загрузки файлов, эффект `Read_package_files`, namespace restoration и преобразование `Error message` разбора в существующий `Eval_error`.

```text
Runner / tests
  -> Pipeline.parse_and_desugar
       -> extension factories + existing OCaml macros
       -> Frontend.parse_and_desugar
  -> Pipeline.create_context
       -> Eval.create_context ~parse_source
            -> deps
                 -> context.parse_source
                 -> eval in existing runtime context
```

Альтернатива — заставить `Eval` вызывать `Pipeline` напрямую — создаёт зависимость по кругу. Callback оставляет `Eval` независимым от верхнего уровня.

### 4. Перевод вызывающих мест

- `bin/runner.ml`: использовать pipeline для полного раскрытия перед выбором target; для eval создавать контекст через pipeline и явно передавать его в `eval_all`. Сохранить source-map параметры и текущий внешний `Gensym.run`.
- `test/test.ml`: перевести прямой JS sample path, который сам разбирает namespace и вызывает компилятор.
- Helpers полного раскрытия в `frontend_desugar_test`, `lowering_test`, `eval_ns_test`, `eval_deps_test`, `js_ns_test`, `java_ns_test`, `java_visibility_test`, `fex_test`, `atoms_test`, `get_in_test`, `instance_check_test`, `eval_stdlib_contracts_test`, `eval_regex_test`, `raw_code_test`: использовать верхний API.
- Helpers, исполняющие язык с контекстом и возможной загрузкой пакетов, создают контекст через `Pipeline.create_context`. Тесты самого низкоуровневого evaluator могут оставаться на `Eval.create_context`; это осознанная граница, не альтернативный путь исполнения полного языка.
- Низкоуровневый frontend остаётся доступен для parser/core-тестов и будущего bootstrap. Его API и список встроенных макросов не меняются.

Новых библиотек и зависимостей Dune не требуется. `test/dune` понадобится только для регистрации нового suite.

### 5. Проверки и простая обработка ошибок

Основные новые проверки сосредоточить в `test/pipeline_test.ml` и существующем `test/eval_deps_test.ml`:

- Пустая конфигурация сохраняет нынешние `cond`, коллекции и метаданные; существующий suite раскрытия проходит через верхний API.
- Простой OCaml-обработчик синтетической формы возвращает форму встроенного макроса; существующий desugar доводит её до core. Никакого кода evaluator для макросов в этом тесте нет.
- После вызова с обработчиком независимый вызов без него не распознаёт синтетическую форму; стандартные макросы работают в обоих случаях.
- Фабрика создаёт обработчик один раз на исходный файл, включая файл с несколькими подходящими формами. Следующий файл получает новую фабричную closure.
- Настроенный обработчик работает в пакете и вложенной зависимости. Тест сохраняет существующие гарантии namespace restoration и порядка `deps`, не повторяя все уже имеющиеся сценарии.

Тестовые расширения существуют только на OCaml-уровне, поэтому отдельные общие `.clj` fixtures для них не нужны. Сохранение поведения обычного языка проверяет существующий sample suite на всех targets.

Исключения распространяются прежним способом: callback не перехватывает и не переименовывает их. Не добавлять префиксы `macro ...`, типы ошибок и новые отрицательные suites. Ошибки compile-time evaluator относятся к следующему этапу, когда такой evaluator появится в раскрытии. Проверки безопасности и существующая диагностика сохраняются.

## Risks / Trade-offs

- **Пропущенный прямой вызов frontend** → проверить все `parse_and_desugar` callers; оставить низкоуровневые вызовы только на сознательно выбранных границах. Особое внимание JS sample runner и `deps`.
- **Разные конфигурации верхнего исходника и пакетов** → тест передаёт один список фабрик и в `parse_and_desugar`, и в `create_context`; runtime callback фиксирует этот список для всех вложенных загрузок. Стандартный runner использует единый default.
- **Утечка состояния обработчика между файлами** → создавать обработчики при каждом вызове раскрытия, не при создании runtime-контекста; проверить фабрикой со счётчиком.
- **Незаметное изменение порядка макросов или Gensym** → сохранять полный встроенный список и текущий обход, использовать существующий `Gensym.run`; не вводить дополнительного AST-прохода.
- **Переусложнение ради будущих макросов** → ограничить добавления двумя API-функциями, типом фабрики и одним callback в eval-контексте. Последующий change расширяет стандартную композицию.

## Migration Plan

1. Добавить callback с прежним default и верхний pipeline с пустым списком дополнительных расширений.
2. Перевести вызывающие места и добавить целевые проверки внутренних точек подключения.
3. Выполнить `make test` и `openspec validate prepare-macro-extension-pipeline --strict`.
4. Интегрировать одним атомарным рефакторингом. Следующий change переносит `cond` отдельно.

Миграции исходников языка и внешних данных нет. Откат рефакторинга возвращает прежние прямые frontend-вызовы; все встроенные макросы всё время остаются на OCaml. Справочник приложения не требует изменения, поскольку пользовательское поведение сохраняется.
