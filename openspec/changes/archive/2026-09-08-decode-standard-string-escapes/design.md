## Context

Мотивация описана в `proposal.md`. `frontend/parser.ml:24-31` потребляет escape-пару через Angstrom и декодирует только `n`; остальные пары восстанавливает буквально. Строка хранится как `SAtom` с внешними кавычками. Eval снимает эту оболочку; обычные строки JS и Java после снятия оболочки передаются в `Target_syntax.string_literal`.

Исключение находится в `backend_compiler/js.ml:33-36`: `frontend/macro_ns.ml` добавляет строковому require ещё одну оболочку, JS снимает её и вставляет оставшийся atom напрямую в source. После декодирования кавычек этот путь может генерировать некорректный JS. Поэтому design нужен для согласования общей семантики frontend и отдельного потребителя в compiler.

## Goals / Non-Goals

**Goals:** сохранить текущий формат AST и разделение ответственности: frontend устанавливает значение, backend сериализует его для target. Исправить обе точки без новой инфраструктуры.

**Non-Goals:** новый string-node, round-trip pretty printer, изменения macro metadata, runtime, загрузчиков модулей, проверки существования module specifiers и диагностики незакрытых строк. Не использовать готовый JSON/OCaml unescaper: его набор escapes и правила ошибок не совпадают с согласованным контрактом.

## Decisions

### Расширить существующий match, не вводить отдельный decoder

В `quoted_string` добавить четыре ветви для кавычки, обратного слеша, TAB и CR к существующей LF-ветви. Сохранить fallback остальных пар и обычные символы без изменений. Потребление пары за один проход естественно обеспечивает, что исходное `"\\n"` не превращается в LF.

Альтернатива с последовательными заменами отклонена: она зависит от порядка и может повторно декодировать результат. Исправление в каждом backend отклонено: все потребители должны получать уже корректное значение.

### Сериализовать строковый require существующим js_string

После определения строкового require снять оставшуюся строковую оболочку через `string_value` и передать payload в `js_string`. Сохранить munging алиаса и не менять символьные namespace requires. Новый serializer или изменение `Target_syntax` не нужны: обычные строки уже используют правильный путь.

### Сохранить неизвестные пары буквально

Это подтверждённая граница изменения, а не временная попытка декодировать весь Clojure. Рядом с fallback уместен короткий `ponytail:` комментарий о намеренном сохранении неподдержанных escapes. Unicode/hex/octal и новые ошибки требуют отдельного решения, не автоматического расширения библиотеки.

### Проверять значения независимо от исходного parser

Расширить `test/frontend_desugar_test.ml` таблицей исходников и точных ожидаемых OCaml payload, включая оболочку `SAtom`: пять escapes, смешанную строку, `"\\n"`, неизвестные пары и HTML. Не строить ожидаемое значение повторным parsing.

В `test/js_ns_test.ml` проверять generated source для HTML, обратного слеша, TAB, CR, LF и отсутствия повторного декодирования; расширить string-require regression кавычкой, обратным слешем, control characters и неизвестной парой. Ожидаемый JS задавать независимо, не через production serializer.

Добавить один общий sample с однострочным результатом для eval/JS/Java: вывести HTML из issue, одиночный обратный слеш и буквальную пару из `"\\n"`. Существующий `string_newline_escape.clj` оставить проверкой LF. Точные payload-тесты и JS-code tests покрывают TAB/CR без управляющих символов в строке ожидаемого вывода. Проверки длины строки через `count` не подходят: текущий eval поддерживает в `count` только collections.

## Risks / Trade-offs

- [Изменение значения существующих строк] -> явно отметить breaking behavior; для буквальной пары использовать экранированный обратный слеш, например `"\\t"` вместо `"\t"`.
- [Parser и expected value могут разделять ошибку] -> ожидаемые payload и JS задаются тестом независимо от frontend и serializer; общий sample проверяет фактический вывод HTML и обратных слешей.
- [Строковый require обходит сериализацию] -> исправить одновременно с parser и покрыть generated import; фактическое разрешение экзотических имён модулей не требуется.
- [Диагностический pretty printer не является serializer] -> сохранить существующее ограничение; не использовать его для обратного parsing и проверки payload.

## Migration Plan

Внедрить parser, string-require emission и regression tests одним изменением. Отформатировать изменённые `.ml` через `ocamlformat -i`, выполнить focused suites и `make test`. Миграции данных и новые зависимости не нужны. Пользовательские строки, намеренно содержавшие буквальные escape-пары, переводятся на `\\`; при откате parser и JS-ветку откатывать согласованно, учитывая уже обновлённые исходники пользователей.
