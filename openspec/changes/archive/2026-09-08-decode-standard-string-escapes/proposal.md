## Why

Issue [#13](https://github.com/y2k/language/issues/13) показывает, что frontend сохраняет обратный слеш перед экранированной кавычкой, поэтому HTML-строка получает лишние символы во время исполнения. После узкого исправления `\n` в #11 нужно определить остальные запрошенные escape-пары до целевой сериализации.

## What Changes

- **BREAKING**: исходные `\"`, `\\`, `\t`, `\r` декодируются соответственно в кавычку, один обратный слеш, TAB и CR вместо сохранения исходной пары; `\n` продолжает означать LF.
- Декодирование выполняется однократно во frontend; неизвестные escape-пары сохраняются буквально, без новых ошибок или поддержки Unicode/hex/octal escapes.
- Строковые JS `:require` сериализуют декодированное значение как JS-литерал, не вставляя его напрямую в generated source.
- Добавляется независимое покрытие значений frontend и JS-кода, включая HTML из issue, однократность декодирования и строковые импорты.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `frontend-syntax`: пять поддержанных escape-пар, однократное декодирование и буквальное сохранение остальных пар.
- `compiler-targets`: корректная сериализация декодированных значений строковых JS module specifiers.
- `open-questions`: убрать неопределённость для escape-пар; оставить открытой диагностику некорректно завершённых строк.

## Impact

Основные точки реализации: `frontend/parser.ml` и строковая ветка `compiler/ns` в `backend_compiler/js.ml`. Проверки используют существующие `test/frontend_desugar_test.ml`, `test/js_ns_test.ml` и при необходимости общий sample harness для eval/JS/Java.

Обычные строки eval и Java получают исправленное значение через общий frontend. AST, lowering, runtime и `Target_syntax.string_literal` менять не требуется; новых зависимостей нет. Программы, рассчитывавшие на буквальные запрошенные escape-пары, должны экранировать обратный слеш через `\\`.
