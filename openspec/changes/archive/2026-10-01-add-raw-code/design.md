# Design

## Context

Мотивация и внешний контракт описаны в `proposal.md` и `specs/compiler-targets/spec.md`. Изменение затрагивает frontend, общий lowering, оба генератора и evaluator, поэтому отдельный design необходим.

Сейчас `frontend/desugar.ml` рекурсивно раскрывает макросы во всех списках; keyword превращается в строковый atom. Парсер уже декодирует поддержанные escapes. `lowering_expression_to_statement.ml` переносит bindings и инструкции из value expressions, поэтому после lowering нельзя надёжно восстановить исходную позицию вставки.

В JS `compile_statement` и top-level `compile` добавляют `;`, а последнее выражение тела получает `return`. В Java `compile_discard` добавляет `;`, `compile_body` делегирует последнюю форму result-emitter, а `compile_statement` допускает только декларации. Top-level Java forms помещаются внутри helper class. Eval использует общий путь вычисления аргументов неизвестных вызовов; raw-code должен перехватываться раньше него.

## Goals / Non-Goals

**Goals:**
- Сохранить строку как непрозрачный фрагмент и обойти обычные expression emitters.
- Сохранить обычный lowering без дополнительного обхода позиций.
- Разделить ошибки Y2K-формы и ошибки произвольного host-кода.

**Non-Goals:**
- Host parser, sandbox, интерполяция, target selection, expression-valued raw-code, Java imports вне класса.
- Регистрация объявленных во фрагменте имён в таблицах функций/locals компилятора, type inference или переписывание имён. Автор использует фактические host identifiers; переносимость ссылок на compiler temporaries не обещается.
- Изменение runtime, системы пользовательских макросов или формата строк/AST.

## Decisions

### 1. Сохранить исходные операнды raw-code при desugaring

В `frontend/desugar.ml` распознавать список с raw-code в head до раскрытия/рекурсивной обработки и сохранять его целиком. Невалидные аргументы также сохранять: compiler увидит исходный keyword/выражение, eval сможет отклонить форму без вычисления аргументов. Не добавлять раскрывающий макрос: требуемое поведение относится к генерации, не к эквивалентной core-expression.

Альтернатива — добавить признак string literal в metadata всех атомов — затронет весь frontend ради одной формы. Проверять только десугаренный string atom недостаточно: keyword уже выглядит как строка. Новая ранняя глобальная ошибка frontend тоже не подходит: она изменила бы поведение eval в недостигнутой ветке.

### 2. Извлечение payload без обхода позиций

`backend_compiler/raw_code.ml` извлекает содержимое литерала для обоих emitters. Локальные ошибки арности/литерала используют координаты формы. По согласованному упрощению проверка дерева до lowering удалена: для компиляции валидного кода она не нужна.

Поддержаны непосредственный top-level и непоследние инструкции тела функции/`let`/`do`. Для условной вставки используется `(do (raw-code "...") nil)` в ветке `if`. Expression-valued вставки не поддерживаются. Нет гарантии отказа по исходной позиции, в том числе в невыбранной ветке: lowering может переместить или удалить формы. Quote остаётся данными.

Для корректной формы lowering сохраняет raw-code как инструкцию без временного результата. Обычная последняя форма продолжает определять значение тела.

### 3. Statement-only generation и top-level placement

В JS добавить отдельное распознавание raw-code в `compile_statement` и в top-level dispatch, возвращающее payload без `;`. В Java — аналогично в `compile_discard` и `compile_statement`. В `compile_expr` обоих targets оставить защитный отказ для raw-code: вставка не должна случайно стать выражением при новом пути генерации. Сам payload не форматируется и не получает отдельный block/IIFE; блоки окружающих `let`, `do`, `if` остаются обычными блоками компилятора.

Top-level dispatch сохраняет порядок исходных форм. Java вставляет фрагмент в существующий helper class; поля, методы, nested classes и явные static blocks пишет автор. JS вставляет фрагмент в module, где автор может написать declaration/import/export. Разделение соседних output-фрагментов переводами строк сохраняется, в том числе чтобы завершающий line comment не поглощал следующую форму. Пустая вставка не создаёт `;`.

Host parser не вводится. Строка с Java `import` на top-level окажется внутри класса и будет отвергнута `javac`, а не автоматически перенесена в prefix. Ошибки синтаксиса и unreachable statements после host `return`/`throw` остаются у host toolchain.

Согласованное уточнение по результатам интеграционной проверки: существующий JS emitter превращал последнюю lowered инструкцию `let* name nil` в statement-блоке отброшенной ветки `if` в expression-вызов `let_STAR_`. В `compile_statement` пустой `let*` block генерируется как обычный `{ ... }` с рекурсивной statement-генерацией всех форм, без returning IIFE. Lowering не изменяется. Регрессия покрыта целевой проверкой и общим `test/samples/discarded_if_blocks.clj` без raw-code.

### 4. Eval rejects reached forms

В `backend_eval/eval.ml` добавить branch для любого списка raw-code до обычного вызова, с Eval_error о поддержке только JS/Java. Не вычислять и не валидировать операнды для исполнения host-кода. Quote и lazy `if` сохраняют существующее поведение. Это соответствует принятому в проекте паттерну instance?.

### 5. Проверки и справочник

- `test/raw_code_test.ml` и регистрация в `test/dune`: exact output boundaries, multiline/escapes/пустая строка, локальные ошибки арности/литерала на обоих targets, сохранение quote, side-effect-free eval rejection.
- `test/lowering_test.ml`, `test/frontend_desugar_test.ml`: исходные операнды и валидная инструкция сохраняются.
- Target-specific samples в `test/samples/js/` и `test/samples/java/`: top-level host declaration и инструкции функции/let/do, порядок эффектов, lambda, выбранный и пропущенный условный путь; результат через `str`, без непереносимого assert.
- `skills/y2k-language/SKILL.md`: английское описание API, примеры для двух targets, escape decoding, допустимые/запрещённые позиции, Java class placement, отсутствие sandbox и name rewriting.

Генерационные тесты нужны отдельно от исполнения: рабочий output не доказывает отсутствие лишнего `;` или изменения пробелов. Интеграционная проверка запускается через `make test` для всех suites/targets.

## Risks / Trade-offs

- [Произвольный код может нарушить синтаксис, scope или безопасность приложения] → Явный escape hatch только для доверенного исходника; host compiler/runtime отвечает за payload.
- [Lowering может превратить неподдержанную value-вставку в statement] → Ответственность автора исходника; ранняя диагностика позиций намеренно не гарантируется.
- [Keyword может выдать себя за исходный строковый литерал] → Сохранение операндов raw-code без desugaring.
- [Различия host scopes и symbol munging] → Не обещать интеграцию host declarations с таблицами языка; примеры используют простые имена и явные host вызовы.
- [Без expression-вставок приходится завершать body обычной формой, например nil] → Намеренное ограничение согласованного контракта; не маскировать результат вставки искусственным значением.

## Migration Plan

Изменение добавляет специальную форму; существующие программы, не использующие raw-code, сохраняют поведение. Пользовательский callable с head raw-code больше не сможет вызываться как обычная функция: имя становится зарезервированным для этой формы. После проверки suites выпускаются compiler и обновлённый справочник совместно. Откат — возврат версии compiler; исходники с новой формой потребуют её удаления или старого interop.
