## Context

Мотивация и API описаны в `proposal.md`; контракт — в `specs/atoms/spec.md`. Design нужен, поскольку добавляется новый runtime value в трёх backend.

В `backend_eval/eval_types.ml` есть только `Symbol`, `List`, `HashMap`, `Closure`. Native-функции получают callback `apply`, уже используемый `map` и `reduce`. Java runtime имеет `call_fn` и `Fn1`; Java compiler умеет генерировать обычные лямбды и прямые вызовы runtime через static import. JS compiler использует явный список импортов, а `!` обрабатывается общим symbol munging.

Уточнение размещения при реализации: `prelude/language_runtime.js` и `prelude/language_runtime.java` являются симлинками соответственно на `/Users/igor/Projects/packages/prelude/1.0.0/js/language_runtime.js` и `/Users/igor/Projects/packages/prelude/1.0.0/java/language_runtime.java`. Изменения этих runtime-файлов учитываются Git в репозитории `packages`, а не в `language`; совместная поставка требует учитывать оба репозитория.

`test/test.ml` автоматически запускает общие `.clj` fixtures на всех targets и сравнивает результат с первой строкой. Eval возвращает наружу только финальный `Symbol`, поэтому общий тест должен возвращать `str` с результатами проверок. Ошибки callback нельзя перехватить общим языковым sample: для этого необходим host-level тест.

Обнаружено расхождение спецификации и кода: закрытый список eval stdlib не включает уже существующий `assert`, который проверяется в `test/eval_ns_test.ml`. Delta сохраняет закрытый список, учитывает `assert` и добавляет четыре новых binding; реализация `assert` не затрагивается.

## Goals / Non-Goals

**Goals:**
- Добавить минимальную ячейку состояния и использовать существующие механизмы вызова функций и запуска тестов.
- Обеспечить общий последовательный контракт и проверки границ API.

**Non-Goals:**
- Новые AST/core-формы, reader-синтаксис, универсальный реестр builtins и изменение общей проверки арности всех функций.
- Конкурентные гарантии, CAS/retry, watchers, validators, сериализация Atom и расширение правил равенства коллекций.

## Decisions

### 1. Отдельное представление ячейки

Eval: вариант `Atom of value ref`. JS: небольшой закрытый runtime-класс Atom с полем значения, позволяющий проверить тип через `instanceof`. Java: небольшой вложенный класс Atom с полем `Object`. Каждый вызов `atom` выделяет новую ячейку; bindings и closures сохраняют ту же ссылку.

List/hash-map в роли ячейки потребовали бы условного распознавания и позволили бы передать обычную коллекцию в `reset!`; поэтому они не подходят. `AtomicReference` с CAS добавил бы другой контракт callback и не нужен для выбранного последовательного объёма.

Новый вариант eval необходимо добавить в исчерпывающие сопоставления, прежде всего `Eval.value_text` и `Eval_stdlib.to_string`. Для диагностического представления достаточно непрозрачного `#<atom>` без обхода содержимого; аналогичное представление в JS/Java предотвращает рекурсию при ссылке Atom на самого себя. Это техническое представление, не формат сериализации. Семантика `=` для Atom этим изменением не стандартизируется.

### 2. Обычные runtime-функции фиксированной арности

Eval регистрирует четыре Native binding и проверяет длину/форму списка аргументов. JS экспортирует `atom`, `deref`, `reset_BANG_`, `swap_BANG_` с явной проверкой `arguments.length`, поскольку сам JS игнорирует лишние аргументы. Java предоставляет по одному методу соответствующей арности с параметрами `Object`; прямые вызовы с неправильным числом аргументов отвергает `javac`.

`backend_compiler/js.ml` дополняет существующий runtime import. Обычная генерация Java-вызовов и лямбд уже достаточна: отдельная ветка compiler для Atom не нужна. Ожидания import в `test/js_ns_test.ml` обновляются вместе с ним.

### 3. Сначала вычислить результат, затем записать

`swap!` проверяет ссылку и вызывает `apply f [old]` в eval, обычную JS-функцию в JS либо `call_fn(f, old)` в Java. После успешного возврата записывает результат и возвращает его. Исключение callback проходит наружу; rollback его побочных эффектов не выполняется. Дополнительные аргументы callback через `swap!` не передаются: внешние данные доступны через lexical closure.

Проверки типа ссылки размещаются в runtime-функциях, а не в compiler. Для JS нужна также проверка вызываемости `f`; eval и Java используют существующий диспетчер вызова. Тексты ошибок могут различаться по target. Общая проверка арности пользовательских JS-лямбд не добавляется.

### 4. Сквозной тест и компактные проверки ошибок

Один `test/samples/atoms.clj` последовательно связывает промежуточные результаты через `let`, чтобы проверять состояние непосредственно после каждого обновления. Он возвращает строку из начального значения, результата и последующего чтения `reset!`, результата и чтения `swap!`, значений alias и независимой ячейки. Дополнительные проверки в том же fixture покрывают `nil`, `false`, list/hash-map, сохранённую функцию, callback с захватом и счётчик вызовов во втором Atom.

Негативные проверки должны реально исполнять runtime: eval с существующим context и перехватом `Eval_error`, JS через Node, Java через `javac`/`java` с перехватом исключения на host-стороне. Использовать существующий Alcotest и настройки `test/dune`; если необходим отдельный компактный `test/atoms_test.ml`, зарегистрировать его там без нового framework. Проверить неправильные арности, неправильные ссылки, невызываемый callback и сохранность значения после ошибки. Проверки generated source сами по себе не заменяют выполнение.

## Risks / Trade-offs

- Новый вариант `value` может сломать исчерпывающие matches → обработать его в диагностике и преобразовании в строку; `dune build` проверит предупреждения.
- JS воспринимает произвольные objects как коллекции в некоторых старых функциях → операции Atom распознают только специальную ячейку; обобщённое переустройство коллекций не требуется для этого API.
- Имя Atom может подразумевать потокобезопасность Clojure → текущий контракт явно ограничен последовательным исполнением; конкурентные гарантии требуют отдельного изменения.
- Мутации делают порядок тестовых выражений наблюдаемым → фиксировать промежуточные значения отдельными последовательными bindings, не полагаться на порядок вычисления аргументов `str`.
- Самоссылки могут зациклить вывод → диагностически печатать непрозрачный маркер без содержимого.

## Migration Plan

Изменение аддитивное. Обновить runtime и JS compiler import совместно, выполнить `ocamlformat -i` для изменённых OCaml-файлов и `make test`. Runtime-файлы поставлять вместе с заново сгенерированным кодом. Откат — совместный возврат runtime, import и новых тестов; миграции данных нет.
