# Design

## Context

См. `proposal.md`. Change следует за `separate-eval-scalar-types`, где уже установлены строгие scalar types и единый lookup map. Текущие builtins используют pattern matching, но `map`/`reduce` проверяют callable только при фактическом вызове. `List.nth_opt` при отрицательном индексе и integer division при нуле могут выбрасывать исключения, которые runner, перехватывающий только `Eval_error`, не обрабатывает как ошибку языка.

## Goals / Non-Goals

**Goals:** явная матрица существующих API и проверка входов независимо от содержимого коллекций; предсказуемые ошибки без расширения успешных операций.

**Non-Goals:** универсальная система signatures, новая подсистема типов, типизация callback до исполнения, новые overloads, порядок для float, политика non-finite/переполнения или изменение callback side effects.

## Decisions

### 1. Проверки остаются рядом с builtin

Сохранить обычный pattern matching для арности и типов. Маленькие helpers для чисел/callable допустимы при повторении, но декларативный registry контрактов не нужен. Матрица в delta-spec описывает все bindings из `Eval_stdlib.env`, включая `assert` и Atom, а не только переносимую часть справочника.

`=` и `not=` сохраняют текущую вариативность: ноль/один аргумент дают соответственно `true`/`false`. `+`, `*`, `str`, `list`, `concat` допускают ноль аргументов; `-` и `/` требуют хотя бы один и не меняют unary-семантику. `/`, порядок, `drop` и list index требуют `Int`, а не float с целым значением.

### 2. Callable проверяется до обхода коллекции

`map`, обе формы `reduce` и `swap!` принимают только `Closure`. Это отвергает `(map 42 [])`, `(reduce 42 0 [])` и `(reduce 42 [1])`. Не анализировать число параметров closure заранее: оно проверяется стандартным вызовом только если callback вызывается. Пустой список с допустимой функцией не вызывает её.

Не менять eager evaluation аргументов: их эффекты уже произошли до входа в builtin. Ошибка тела callback пробрасывается без общего перехвата и переименования в ошибку `map`/`reduce`/`swap!`. При неуспехе `swap!` сохраняет прежнюю гарантию отсутствия финальной записи, но не отменяет побочные эффекты callback.

### 3. Ожидаемые ошибки нормализуются узко

Проверять отрицательный list index до обращения к списку, нулевой делитель до деления. Не перехватывать все исключения в runner: это скрывает внутренние дефекты. В `slurp` сохранить error для файловой операции, добавить обработку недопустимого пути (например, NUL) в месте вызова файлового API.

Ошибки аргументов называют builtin и ожидаемую арность/тип; ошибки операции называют причину. Существующие точные сообщения `assertion failed`, `hash-map arguments must be key/value pairs`, `slurp expects one path`, `slurp failed: PATH` сохраняются. Остальные тексты не являются стабильным форматом; тесты проверяют `Eval_error`, имя операции и категорию причины. `Runner.run` должен вернуть `Error message`, CLI — ненулевой статус.

### 4. Lookup не переписывается повторно

Числовое равенство и shared lookup уже часть второго change. Здесь матрица и регрессии закрепляют одинаковое поведение `get`, `get-in` и деструктуризации, в том числе сохранение первого из эквивалентных ключей и несовпадение строк/чисел/boolean. Для `get nil key` сохраняется возврат nil независимо от key; в `get-in` тип всего пути проверяется даже при исходном nil, но после отсутствующего промежуточного значения оставшиеся элементы пути не превращаются в list index без списка.

### 5. Один целевой suite для матрицы

Добавить `test/eval_stdlib_contracts_test.ml` с таблицами корректных/некорректных вызовов и зарегистрировать в `test/dune`. Для фиксированных арностей проверить отсутствие/лишний аргумент, для variadic — границы и неправильный элемент. Дополнить существующие get-in/Atom проверки там, где это сохраняет контекст побочных эффектов. Общие успешные сценарии — в `test/samples/`, eval-specific ошибки — в целевом suite или `test/samples/eval/`. После обновления tests выполнить `make test`.

## Risks / Trade-offs

- Более ранняя ошибка на пустых коллекциях ломает случайно работавший код → явно описать breaking change и дать тесты пустых/одноэлементных коллекций.
- Ужесточение случайно меняет успешные unary/variadic вызовы → positive boundary cases в той же матрице, что и ошибки.
- Общий перехват скрывает ошибку callback → перехватывать только ожидаемые исключения конкретной host-операции.
- Третий change не должен заново менять модель equality → использовать helper второго change и тестировать согласованность consumers.

## Migration Plan

Применять только после второго change, обновить справочник в той же реализации и выполнить полную проверку. Исправление клиентского кода — передавать значения правильных типов и callable даже для пустых коллекций. Откат локален этому change, оставляя boolean и scalar types предыдущих этапов. При синхронизации deltas сохранить все ранее добавленные сценарии и согласованный порядок changes.

### Сверка baseline

Boolean и scalar changes уже интегрированы в main spec и архивированы. Этот delta заменяет только требования get-in и неопределённого поведения, сохраняя имена всех их текущих сценариев, и добавляет четыре требования контрактов. Он не заменяет scalar/boolean, runner, lookup, control либо stdlib-блок предыдущих changes. При отдельной интеграции ещё активных завершённых nil/Atom changes нужно сохранять эту новую семантику, а не применять их старые MODIFIED-блоки поверх неё.
