# Design

## Context

Работа охватывает два репозитория по подтверждению пользователя: compiler/tests/docs/artifacts в `~/project/language`, runtime в `~/project/packages/prelude/1.0.0/js/language_runtime.js` и `~/project/packages/prelude/1.0.0/java/language_runtime.java`. Пути `language/prelude/language_runtime.*` — symlinks на эти файлы, поэтому language commit не содержит runtime diff. Существовавшие до реализации незакоммиченные regex API и исправления truthiness в packages сохраняются.

Мотивация — в `proposal.md`. Regex уже реализован в трёх runtimes, но JS generator не включает `re_pattern`, `re_find`, `re_replace` в import. Eval использует Re 1.13.2 и имеет отдельный suite `test/eval_regex_test.ml`; Unicode-проверки этого suite намеренно побайтовые.

JS хранит regex в `Regex` с `RegExp`, Java — в `java.util.regex.Pattern`. JS replacement использует native global replace с callback для буквальности, Java — `Matcher.replaceAll` с `quoteReplacement`. JS сравнивает значения через `Object.is`, Java через `Objects.equals`: один regex сейчас равен себе. Java уже нормализует `$` вне классов в `\z`; JS без multiline имеет строгий конец строки. Оба target уже печатают `#<regex>` через str.

Compiled hash-map хранит текстовые ключи, JS equality не структурное, Java equality использует host collections. Поэтому перенос eval-правил рекурсивного равенства и regex-ключей потребовал бы отдельного изменения модели коллекций. Нынешняя `compiler-targets` спецификация гарантирует только бинарное равенство скаляров; новые regex-требования добавляются отдельными ADDED blocks, не заменяя его.

## Goals / Non-Goals

**Goals:** Минимальные adapters в существующих runtime-функциях; единый проверяемый контракт из `specs/compiler-targets/spec.md`; выполнение тестов через настоящую компиляцию, Node и JVM.

**Non-Goals:** Новый regex parser/engine, перенос Re в JS/WASM, новые зависимости, единый Unicode, проверка всего синтаксиса на соответствие portable subset. Не меняем представление коллекций, рекурсивное равенство, regex map keys и правила вывода произвольного финального значения. API принимает runtime-строки: отдельный Symbol в eval не превращается в требование нового Symbol-типа compiled targets. Первый класс regex-значений не означает расширение поддержки first-class builtin function references.

## Decisions

### 1. Существующие bindings и движки

Добавить три имени в стандартный import `backend_compiler/js.ml`, сохранив вычисление пути для вложенных namespaces. Java использует существующий static import. Сохранить текущие представления regex и локальные проверки аргументов; отдельная Java wrapper class не нужна для прямого сравнения.

Альтернатива — единый движок — существенно увеличивает поставку и поддержку ради семантики, которая пользователю не нужна. Общий контракт ограничен печатным ASCII, TAB и LF; остальные управляющие символы и Unicode явно оставлены target-specific. Это не ограничение допустимого входа, а граница гарантии равных результатов.

### 2. Прямое бинарное равенство

В `_EQ_` обоих runtimes проверять непосредственные regex-операнды перед существующим сравнением. `not_EQ_` продолжает отрицать `_EQ_`. Другие типы и сравнения коллекций используют текущую реализацию. Это выравнивает согласованное поведение `(= r r)` без новой универсальной системы равенства.

Regex остаётся истинным и не-callable; существующие пути str и передачи через bindings, обычные map values, destructuring и Atom подтверждаются общими fixtures. Ошибки прямого вызова проверяются на неуспешность, без обещания одинакового host exception или слова regex.

### 3. Управление обходом при замене

Нативный поиск сохранить, а обход replacement сделать явным: JS — отдельный global matcher на каждый вызов, Java — новый Matcher. Разделить позицию поиска, начало ещё не скопированного исходного текста и конец предыдущего непустого совпадения. Добавлять исходные slices и replacement напрямую, не используя синтаксис подстановки host API.

- Непустое совпадение заменяется, поиск продолжается от его конца.
- Пустое совпадение непосредственно в конце предыдущего непустого пропускается.
- После любого пустого совпадения поиск продвигается на одну native text unit, если она существует; исходный символ сохраняется через последующее копирование исходного текста.
- На конце строки цикл завершается, не повторяя пустое совпадение.
- Работа идёт по полному исходному text, а не по обрезанному суффиксу: `^` не должен начать совпадать заново после продвижения.

Для переносимого ASCII native unit совпадает с байтом eval. Для непереносимого Unicode сохраняется target-specific обработка; это явно документируется. Массив фрагментов с join в JS и StringBuilder в Java избегают многократного копирования всего результата. Matcher state не хранится между вызовами.

Альтернатива — оставить native replace — не обеспечивает eval-правило `a*` в `ab` → `-b-`. Общая абстракция regex-движков не нужна: каждый adapter мал и находится рядом с существующим API.

### 4. Anchors и диалекты

Сохранить JS anchors без флагов и Java-нормализацию `$` в `\z`. Проверить escaped dollar, dollar внутри класса, повторный глобальный обход и финальный LF. Не заменять текст шаблона глобальной строковой подстановкой: экранированные метасимволы и классы обязаны сохранять смысл. Исправлять существующий Java scanner только в пределах переносимой грамматики, если тесты выявят проблему.

Дополнительные конструкции native engines могут работать на JS/Java, хотя eval их отвергает. Не вводить allowlist/parser для синхронного отказа. Справочник должен отделять переносимые примеры от native extensions и не обещать полного совпадения Re.Perl, ECMAScript RegExp и Java Pattern.

### 5. Проверка через исходники языка

Общие положительные сценарии разместить в `test/samples/regex_*.clj`: API/import, классы, anchors, greedy/lazy, bounded quantifiers, пустые совпадения, буквальность, повторное использование, непосредственное равенство и передача значения. Результаты проверять бинарными `=`/`not=` и условиями, выводить через str; assert в общих fixtures не использовать. Так nil и строка `"nil"` не перепутаются по одинаковому выводу.

Отрицательные сценарии добавить в `test/regex_targets_test.ml` по образцу `test/get_in_test.ml`: сгенерировать функции языка, реально скомпилировать Java, вызвать их из host harness, проверить имя builtin и причину. Покрыть обе неверные стороны арности каждого builtin, неверные типы во всех позициях, пустой text, callback, malformed pattern. Отдельно проверить необработанную ошибку процесса (stderr и ненулевой status), не принимая провал javac за успешную проверку runtime error. Java varargs с единственным nil требует отдельного case из-за возможного null array.

Eval-only диалектные, Unicode, quoted-symbol, collection-key и runner cases остаются в существующем suite. Сохранить userscript integration: новый import должен по-прежнему удаляться имеющимся сборочным примером. Полная проверка — `make test`.

## Risks / Trade-offs

- [Native dialects шире portable subset] → точный список поддерживаемых переносимых конструкций, общие fixtures; расширения не обещаются и не запрещаются общей проверкой.
- [Ошибки прогресса пустого совпадения и anchors] → отдельные cases для пустого text, конца после непустого совпадения, `^`, `$`, пустого replacement и повторного использования r; ограничить время запуска host tests.
- [Ложное впечатление полной синхронизации] → справочник явно разделяет прямое равенство regex, collection equality, map keys, Unicode и runner output.
- [Изменение существующего JS/Java поведения] → отметить binary regex equality и zero-width replacement как breaking; проверить сохранение скалярного равенства существующими suites.

## Migration Plan

Поставка состоит из согласованной пары изменений: companion runtime в packages и compiler/tests/docs в language. Сначала включить runtime с тремя regex exports, проверками аргументов, str и согласованными replacement/equality, затем compiler с новым import; существующее исправление truthiness строк в runtime сохранить как зависимость текущих language tests. Публикация одного language commit без companion runtime недопустима. При создании коммитов связать их SHA в описании поставки; создание коммитов и публикация выполняются по отдельному запросу пользователя.

Перекомпилировать потребительские исходники и обновить копии runtime вместе: generated JS с новыми imports требует соответствующего runtime. Миграции данных нет. При откате сначала вернуть compiler и перегенерировать JS, затем при необходимости вернуть runtime к совместимой версии, сохраняя ранее согласованные исправления truthiness. Проверка пары выполняется через `make test` в language: dune использует реальные companion-файлы через symlinks. Проверять `git diff --check` в обоих репозиториях.
