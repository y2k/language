## Context

Мотивация описана в `proposal.md`. OpenCode загружает `SKILL.md` из каталога скилла; переносимость достигается симлинком всего каталога. В приложениях уже доступны `ly2k` и сборка, доставляющая runtime. README, спецификации и реализация имеют разную полноту: например, README ограничивает Java function values арностями 0–2, тогда как runtime содержит `Fn0`–`Fn4` и существуют соответствующие тесты.

Документ фиксирует технические решения по границе общего справочника, target-specific разделу и актуализации: эти неоднозначности требуют согласования до подготовки содержимого.

## Goals / Non-Goals

**Goals:**
- Сделать один файл пригодным для чтения из любого проекта приложения без привязки к рабочему каталогу компилятора.
- Дать полный пользовательский справочник в согласованных границах, сохраняя компактность таблицами сигнатур и короткими примерами.
- Проверять применимость возможностей по targets, а не только наличие frontend-формы.

**Non-Goals:**
- Генератор документации, установщик скилла и справочники для нескольких версий.
- Обучение разработке самого компилятора или описание внутренних lowering forms как API.
- Изменение сборки приложений, runtime или существующей семантики языка.

## Decisions

### Один каталог и один SKILL.md

Источник — `skills/y2k-language/SKILL.md`; потребитель подключает каталог в `.opencode/skills/y2k-language`. Frontmatter содержит `name: y2k-language` и описание с явными триггерами Y2K Language и `ly2k`. Весь файл англоязычный. Ссылки на репозиторий абсолютные; локальные пути автора не используются.

Альтернатива — несколько reference-файлов — пока не нужна: один файл проще распространять и проверять на полноту. Симлинк каталога оставляет возможность разделить документ позднее без изменения точки подключения. Намеренное отсутствие версионированного справочника можно обозначить кратким HTML-комментарием `ponytail:` с указанием перехода к версиям при появлении такой потребности.

### Общее и target-specific описываются раздельно

Структура файла:
1. Назначение, отличие от Clojure и выбор target по проекту.
2. Общие пользовательские формы, синтаксис и семантика.
3. Кроссплатформенная стандартная библиотека с сигнатурами и ограничениями.
4. Отдельный раздел target-specific возможностей: `eval`, JavaScript, Java, включая `export-default`, `gen-class`, namespaces и interop в соответствующих границах.
5. CLI и работа с существующей сборкой приложения.
6. Репозиторий и issues.

Кроссплатформенность функции означает её доступность на всех трёх targets, а не автоматическое равенство всех перегрузок и edge cases. Различия арностей и поведения фиксируются явно. Альтернатива — единый список без target-раздела — скрывает ограничения и противоречит согласованной структуре.

### Инвентаризация по исходникам и тестам

При реализации сопоставить parser/macros, обработчики backend и публичные функции evaluator и runtimes. Затем сверить пользовательские формы и пересечение стандартной библиотеки с существующими спецификациями и тестами, включая завершённые, но ещё не архивированные изменения вроде `add-atoms`. Не считать наличие формы во frontend доказательством поддержки каждым backend. Неопределённое поведение не превращать в обещание скилла.

Вместо нового генератора документации использовать ручную сверку полного списка. Короткие примеры брать из проверенных тестов; новые примеры проверять соответствующим target. Для JS/Java одной успешной генерации недостаточно, если пример обещает результат исполнения.

### CLI отражает окружение приложения

Примеры используют `ly2k --target eval|js|java` с конкретным target в каждой команде, stdin и перенаправление generated source. Runtime доставляет сборка; инструкции не предлагают копирование из `prelude/`. Выполнение приложения следует его собственным build/run-командам, поскольку генерация Java или JS сама по себе не запускает приложение.

### Актуальность поддерживается правилом разработки

Добавить в корневой `AGENTS.md` краткое правило обновления `skills/y2k-language/SKILL.md` при изменении пользовательских форм, описываемой библиотеки и ограничений targets. Скилл соответствует текущей реализации; пользователь обновляет установленный `ly2k` вместе с компилятором. Альтернатива — version matrix — избыточна для согласованного сценария.

## Risks / Trade-offs

- Расхождение справочника с реализацией → сверка с тестами и обязательное обновление при изменении пользовательских возможностей.
- Новый текст по симлинку при старом `ly2k` → явно обозначить ориентацию на текущий компилятор, не обещать совместимость со старыми версиями.
- Полнота увеличивает контекст агента → компактные таблицы, примеры для существенных случаев, отсутствие пересказа внутренних алгоритмов.
- Отличия target маскируются общим frontend → проверять backend и runtime отдельно, отражать ограничения рядом с сигнатурами и в target-specific разделе.

## Migration Plan

После создания скилла пользователь подключает его каталог симлинком в существующий каталог скиллов приложения и перезапускает OpenCode. Проверка обнаружения выполняется в отдельном временном проекте, не в пользовательском приложении. Для отката достаточно удалить созданный симлинк и перезапустить OpenCode; исходный каталог скилла остаётся в репозитории компилятора.
